# 検証観点（必ず実際にファイルを読んで確認する）

## 1. セキュリティ設定（settings.py / config/ — 最優先）
- **`DEBUG`**: `True` がハードコードされていないか。環境変数化されているか（`os.getenv("DJANGO_DEBUG", "False") == "True"` 等）。研修の典型論点なので必ず指摘する。
- **`ALLOWED_HOSTS`**: 空のまま放置されていないか。`DEBUG=False` で動作するか。二重定義がないか。
- **`SECRET_KEY`**: 環境変数化されているか。`"django-insecure-..."` 等のデフォルト値で起動できてしまわないか。
- **CORS**: `CORS_ALLOW_ALL_ORIGINS=True` を使っていないか。許可オリジンが環境変数化されているか。自前ミドルウェアがある場合はOrigin照合・Vary・プリフライト処理の妥当性。
- Swagger/OpenAPI スキーマが `DEBUG` 等で本番に漏れない出し分けになっているか。

## 2. 設定の集約と環境変数化
- **Django settings を実際に参照しているか**: 設定値（許可オリジン・各種フラグ・タイムアウト等）を `settings.py` に集約し `django.conf.settings` 経由で参照しているか。views/serializer 側に同等の値をハードコードして二重管理になっていないか。テストで `@override_settings` 等が使える構造か。
- **エンドポイント/外部URLの環境変数化**: バックエンドが叩く外部APIのURL、許可オリジン、ベースURL、ポート等が **環境変数化**されているか（`os.getenv` / `django-environ` 等）。ソースに直書きされていないか。
- 環境変数の **デフォルト値が安全側**か（本番向けの値がハードコードされていないか）。`.env.example` 等で必要な変数が文書化されているか。

## 3. API設計（DRF / REST）とエラーハンドリング（views.py / urls.py / serializers.py）

**前提アーキテクチャ**: 本課題は **Django REST Framework (DRF)** を使う前提（DjangoのMVTをベースにAPI開発へ特化した構成）。フロントは別の React アプリなので Template は使わず、View/Serializer を中心に JSON API として成立しているか確認する。役判定はDBを持たない計算APIになりがちなので、Model/ORM が不要なら無理に使っていないかも見る（Serializer は `Serializer` ベースで成立しうる）。

### 3.1 DRF コンポーネントの妥当性
- **Serializer（シリアライズ/デシリアライズの双方向を見る）**:
  - **デシリアライズ（入力 JSON → Python）**: リクエストの検証（枚数=5・カード表記・重複）を Serializer の `fields` / `validate_*` / `validate()` に寄せ、`is_valid()` / `validated_data` を経由しているか。View 内の手書き検証や生 `request.data` 直読みに散らばっていないか。`ListField(child=..., min_length=5, max_length=5)` 等で枚数制約を型で表現できているか。
  - **シリアライズ（判定結果 → 出力 JSON）**: レスポンス（役名・最強カード・各プレイヤー順位等）を **出力用 Serializer** で構築しているか、それとも View で dict を手組みして `Response(...)` に直接渡しているか。入力用と出力用で Serializer を分けるべきか（責務が混ざっていないか）を見る。
  - **双方向の対称性**: 入力で受けるカード表記と出力で返す表記が一貫しているか。シリアライズ時の型（数値/文字列/enum）が安定しているか。
  - `Serializer` と `ModelSerializer` の選択が妥当か（DBモデルが無いなら素の `Serializer`。判定結果はDBに永続化しないので `ModelSerializer` は通常不適）。
- **View / ViewSet / APIView**: 単一の役判定エンドポイントに `ModelViewSet`（CRUD前提）を流用して過剰になっていないか。計算系なら `APIView` か関数ベース+`@api_view` が素直。選択理由が構成と整合しているか。
- **Router**: CRUD でない単一エンドポイントに Router を使って不自然なURLを生成していないか。逆に ViewSet なら Router で素直に登録しているか。
- **認証・パーミッション**: 公開APIとして妥当な `permission_classes` か（不要な `IsAuthenticated` で塞いでいないか／無防備すぎないか）。`csrf_exempt` 乱用でなく DRF の仕組みで処理しているか。
- **DRFの標準機構を活かしているか**: ステータス返却に `rest_framework.status`、レスポンスに `Response`、エラーに DRF の例外（`ValidationError` 等）を使い、素のJsonResponse手組みに退化していないか。

### 3.2 REST API としての設計妥当性
- **リソース指向のURL**か（動詞をURLに埋め込んでいないか。例: `/api/evaluate/` のような名詞ベースか、`/getHandResult` のような RPC 風でないか）。役判定は「判定リクエスト」というリソースとして妥当に表現されているか。末尾スラッシュ・プレフィックスの一貫性、仕様書のエンドポイントとの整合も見る。
- **HTTPメソッドの使い分け**が REST 的か（判定リクエストの送信は副作用の有無に応じ POST が妥当。GET でボディを要求していないか。許可外メソッドに 405 を返すか）。
- **ステータスコードが REST 的に意味整合**しているか（成功 200/201、クライアント起因 4xx、サーバ起因 5xx の区別。400=不正リクエスト形式 / 422=値が無効 / 405=メソッド不正 等の使い分け）。`status.HTTP_*` 定数を使っているか、生の数値か。
- レスポンス形状が一貫しているか（成功・エラーで構造が揃っているか、`Content-Type: application/json` か）。エラーレスポンスの形状がフロントと密結合していないか、メッセージ言語は妥当か。
- DRF の機能を REST 的に正しく使えているか（ステータス・例外・ページネーション等は規模相応か。役判定APIに対し過剰な機能を盛っていないか）を設計判断として一言添える。

### 3.3 エラーハンドリングの分担
- JSONパースエラー・型エラー・値エラーを区別してハンドリングしているか。
- 入力バリデーションの責務分担。枚数・形式・重複チェックが serializer 層にあるか、ロジック層任せか（理想は serializer 層に集約）。

## 4. SOLID原則の遵守（設計品質）
研修課題として設計の妥当性を評価する。過剰設計は求めないが、以下の観点で明確な違反があれば指摘する。
- **SRP（単一責任）**: view が「リクエスト解釈・バリデーション・役判定ロジック・レスポンス整形」を一手に抱えていないか。役判定はロジック層に分離されているか。
- **OCP / DIP（拡張・依存方向）**: view が具体実装に直結せず、ロジック層を関数/インターフェース越しに呼んでいるか。新しい役やレスポンス形式の追加時に view を改変せず済む構造か。
- **ISP / LSP**: serializer やユーティリティが用途過多な巨大クラスになっていないか。継承を使っている場合に基底の契約を壊していないか。
- 指摘時は「どの原則に・なぜ違反し・どう分割すべきか」を具体的に書く。原則名の羅列だけにしない。

## 5. クリーンコード（実装の作法）
SOLID（設計の原則）とは別に、コードの読みやすさ・保守性を実装レベルで評価する。

### 5.1 可読性・命名・関数粒度
- 変数/関数/クラス名が意図を表しているか（`d` `tmp` `data2` のような曖昧名、`flag` 等の無意味名がないか）。
- 関数が短く単一の処理に収まっているか。1関数に多段の `if`/ループが詰まり認知負荷が高くないか。
- **マジックナンバー/文字列**（`5`（手札枚数）、ランク・スートの文字列、ステータス数値等）が定数・enum 化されているか。
- コメントが「何を」ではなく「なぜ」を説明しているか。コメントアウトされた死にコード・無意味なコメントが残っていないか。
- **DRY**: 同じ判定・変換・整形ロジックが複数箇所にコピペされていないか。

### 5.2 エラー処理の作法
- 例外を**戻り値コード/特殊値（-1, None, 空文字）で代替していない**か。異常は例外で表現しているか。
- 例外の**粒度**が適切か（`except Exception:` の握りつぶし・bare `except:` がないか。捕捉した例外を握り潰さずログ/再送出しているか）。
- null/空・境界（カード0枚、想定外キー）の扱いが明示的か。
- DRF 文脈ではドメイン例外を `ValidationError` 等へ適切に変換し、スタックトレースを生レスポンスに漏らしていないか。

### 5.3 層分離・依存方向（Clean Architecture 寄り）
- **view / serializer / ビジネスロジック（役判定）の層境界が明確**か。役判定ロジックが view や serializer に溶け込んでいないか、独立モジュールとして切り出されているか。
- 依存方向が「外側（view/DRF）→ 内側（純粋な役判定ロジック）」の一方向か。役判定ロジックが Django/DRF（`Request`, `Response`, `settings` 等）に依存していないか（＝フレームワーク非依存でユニットテスト可能か）。
- ※ SOLID の DIP と一部重なるが、ここでは「層の物理的な分離とフレームワーク非依存性」を具体的に見る。

## 6. ログ設計
- **そもそもログ設計があるか**: `print` でのデバッグ出力に頼らず、Django の `LOGGING` 設定（`settings.py`）または `logging.getLogger(__name__)` を使ったロギングが設計されているか。研修でも欠落しやすいので必ず確認する。
- **構造化ログ / リクエストログのミドルウェア**: アクセスログやリクエスト/レスポンスを記録する仕組み（カスタムミドルウェア、`django-structlog` / `structlog` / JSON フォーマッタ等）が導入されているか。導入が無い場合は、運用観点で「構造化ログ or リクエストロギング middleware の検討余地」を指摘する。
- **ログレベルの使い分け**: `DEBUG/INFO/WARNING/ERROR` を意味に応じて使い分けているか。例外捕捉時に `logger.exception()` 等でスタックトレースを残しているか（握り潰して無言で握り潰していないか）。
- **機微情報の漏洩**: ログにシークレット・全リクエストボディ等の機微情報をそのまま出していないか。
- **出力先と環境差**: ハンドラ（コンソール/ファイル）の設定が妥当か、`DEBUG` 等で出力先・レベルを環境ごとに出し分けているか。
- ※役判定APIは小規模だが、研修課題として「観測可能性（誰がいつ何を叩き、どこで失敗したか追えるか）」の設計意図があるかを評価する。

## 7. 仕様との差分
仕様書（docs/ 等があれば読む）とフレームワーク選択・エンドポイントがズレていないか。ズレている場合 README で説明されているか。
