# DDD: 既存コードのリファクタリング (Legacy → DDD)

他の DDD スキルは**新規に正しく書く**前提。ここは**すでにあるコードを動かしながら
寄せていく**手順を扱う。前提が違うので、判断も違う。

**大原則: 動いているコードを壊さないことが、設計の美しさより優先する。**

移行先の設計は
[ddd-domain-object-completeness](../ddd-domain-object-completeness/SKILL.md) /
[ddd-aggregate-repository-boundary](../ddd-aggregate-repository-boundary/SKILL.md) /
[ddd-application-layer](../ddd-application-layer/SKILL.md)、
そもそも何をモデルにするかは
[ddd-modeling-discovery](../ddd-modeling-discovery/SKILL.md)、
テストの書き方は
[ddd-testing-strategy](../ddd-testing-strategy/SKILL.md)。

---

## 1. 全部を DDD にしない

**最初の判断は「どこをやらないか」。** 全面 DDD 化は、たいてい途中で力尽きて
「半分だけ DDD」という最悪の状態を残す。

| 対象 | 判断 |
| --- | --- |
| **コアドメイン**(競合優位の源泉) | やる。ここだけでよい |
| 支援サブドメイン | やらない。CRUD のままで困らない |
| 汎用サブドメイン(認証・通知・帳票) | やらない |
| **変更が頻繁でバグが多い箇所** | やる。投資が回収できる |
| 数年触っていないコード | やらない。動いているものを触らない |

分類は
[ddd-bounded-context](../ddd-bounded-context/SKILL.md)。

**着手の順序**: 「重要 × よく壊れる」から。「簡単そうだから」で選ばない —
簡単な箇所は CRUD のままで足りていることが多い。

---

## 2. 動かす前にテストで囲う

**リファクタリングは「振る舞いを変えない変更」。** 変わっていないことを確かめる
手段がなければ、それはリファクタリングではなくただの書き直し。

- 既存の振る舞いを**そのまま**固定するテスト(特性テスト / characterization test)を先に書く。
  **正しいかどうかは問わない** — バグも含めて現状を記録する。
- 移行対象の**入口と出口**でテストする(view → DB の結果)。内部実装を検証すると、
  動かした瞬間に全部落ちる。
- テストが書けないほど絡まっているなら、**まず絡まりを解く小さな変更**だけを先にやる。
- 「振る舞いを変える」変更(バグ修正・仕様変更)を**同じコミットに混ぜない**。
  混ぜると、壊したのがどちらか分からなくなる。

## 3. 値オブジェクトから始める

**最も安全で、最も効果が出るのが値オブジェクト。** エンティティより先にやる。

- 影響範囲が狭い(そのフィールドを使う箇所だけ)。
- Django モデルを触らずに導入できる。
- 導入した瞬間にバリデーションが全呼び出し側へ効く。

```python
# Before: 裸の str。バリデーションが呼び出し側に散らばる
class CustomerModel(models.Model):
    email = models.EmailField()

# Step 1: ドメイン層に値オブジェクトを作る(既存コードはまだ触らない)
@dataclass(frozen=True, kw_only=True)
class Email(ValueObject):
    value: str

    def __post_init__(self) -> None:
        if "@" not in self.value:
            raise ValueError(f"不正なメールアドレス: {self.value!r}")

# Step 2: 境界(モデル ↔ ドメイン)で変換する箇所を1つずつ置き換える
```

順序: **値オブジェクト → エンティティ → 集約 → リポジトリ → usecase。**
逆順(いきなり usecase 層を作る)にすると、中身が空のまま層だけ増える。

## 4. 太った Django モデルからエンティティを切り出す

**Django モデルは消さない。** 永続化モデルとして残し、その隣にドメインエンティティを
作って、ロジックだけを移す。

```python
# Before: モデルにロジックが溜まっている
class OrderModel(models.Model):
    status = models.CharField(max_length=20)

    def cancel(self):                       # ← ドメインロジック
        if self.status == "shipped":
            raise ValidationError("出荷済みは取り消せない")
        self.status = "cancelled"
        self.save()                         # ← 永続化が混ざっている
```

手順:

1. **ロジックと永続化を分離する。** 上の `cancel` は「判断 + 状態変更」と「保存」が
   混ざっている。まず保存を呼び出し側へ追い出す。
2. **ドメインエンティティを作る。** stdlib のみ、frozen。
   Django を import しない。
3. **変換関数を書く**(`OrderModel` ⇄ `Order`)。最初はモジュール関数でよい。
4. **1メソッドずつ移す。** モデルのメソッドは残したまま、中でドメインへ委譲する。
   全部の呼び出し側が移り終えたら、モデル側を削除する。

```python
# Step 3: 委譲でつなぐ(呼び出し側は当面そのまま動く)
class OrderModel(models.Model):
    def cancel(self):
        order = to_domain(self)             # ドメインへ
        cancelled = order.cancel()          # 判断はドメイン
        apply_to_model(self, cancelled)     # 結果を書き戻す
        self.save()
```

- **一度に全部やらない。** 1つの振る舞いを移す → テストが緑 → コミット、を繰り返す。
- **`ValidationError` を `ValueError` に置き換える**のは、ドメイン側だけ。
  インターフェース層で従来の例外に変換して互換を保つ。
- 切り出しの単位は**振る舞い**。フィールドをまとめて移そうとしない。

### エンティティを複数に割る判断

切り出しの途中で「1つのエンティティが大きすぎる」と分かることがある。

| サイン | 割り方 |
| --- | --- |
| フィールド群ごとに使う場面が完全に分かれる | 別エンティティ(別集約)へ |
| 一部だけ更新頻度が極端に高い | 変更頻度の軸で割る |
| 状態によって使われないフィールドが大量にある | 状態ごとに別の型(または状態オブジェクト) |
| メソッドが触るフィールドが2グループに分かれる | そのままの線で割れる |

判断基準は
[ddd-aggregate-repository-boundary](../ddd-aggregate-repository-boundary/SKILL.md)
の「一緒でないと不正になるもの」。**割ってよいのは、同時に守るべき不変条件がない場合だけ。**

## 5. `XxxService` を解体する

`OrderService` のような「なんでも屋」は、**中身が3種類混ざっている**。
仕分けてから配る。

| 中身 | 移す先 |
| --- | --- |
| 業務ルールの判断(`if` と計算) | **エンティティ / 値オブジェクト** |
| どのオブジェクトにも属さない判断 | ドメインサービス([ddd-domain-service-specification](../ddd-domain-service-specification/SKILL.md)) |
| 取得 → 呼び出し → 保存の手順 | **usecase**([ddd-application-layer](../ddd-application-layer/SKILL.md)) |
| 検索・一覧・集計 | query service([ddd-read-model-cqrs](../ddd-read-model-cqrs/SKILL.md)) |

手順:

1. public メソッドを列挙し、**1メソッド = 1 usecase 候補**として分類する。
2. メソッド内の `if` を見て、**ドメインの言葉で説明できるもの**をエンティティへ移す。
3. 残った「取得・保存・通知」の並びが usecase の中身になる。
4. メソッドを1つずつ新しい usecase クラスへ移す。移し終えたメソッドは
   Service から削除する。
5. Service が空になったら削除する。

**「ドメインサービスに移す」に逃げない。** 名前を変えただけで貧血症は直らない。
まずエンティティに置けないかを疑う。

## 6. リポジトリを後から挟む

usecase が `OrderModel.objects` を直接触っている状態から、抽象を挟む。

1. **抽象を先に定義**(`OrderRepository`、ドメイン層)。
2. **実装は既存クエリをそのまま移す。** この段階では最適化しない。
3. usecase のコンストラクタで受け取るよう変える。
4. テストを in-memory 実装に差し替える
   ([ddd-testing-strategy](../ddd-testing-strategy/SKILL.md))。

- **検索メソッドを抽象に入れない。** 移行中に見つかった検索は query service 側へ
  分ける。ここで妥協すると、リポジトリが元の Manager に戻る。
- 具象の選択は composition root 1か所へ。

---

## 7. 新旧の共存期間を設計する

移行中は**必ず**新旧が同居する。その期間を無計画にすると、両方壊れる。

- **境界を1か所に決める。** 「この view 以下は新、それ以外は旧」のように、
  ファイル単位で線を引く。混在をファイル内に持ち込まない。
- **同じ業務ルールを2箇所に書かない。** 旧コードからも新しいドメインオブジェクトを
  呼ぶ(第4節の委譲)。二重実装は必ずズレる。
- **書き込み経路は早く一本化する。** 読み取りの二重化は許容できるが、書き込みが
  2経路あると不変条件が守れない。
- **期限を決める。** 「そのうち移行」は残り続ける。移行しないと決めたなら、
  その旨を書いて閉じる。

---

## 8. どこで止めるか

**全部を DDD にするのがゴールではない。** 次のどれかに当たったら止めてよい。

- 対象がコアドメインでないと分かった。
- 変更頻度が下がり、投資が回収できない。
- 移行の残りが「フレームワークとの摩擦」だけになった(層のための層)。

止めるときは、**どこまでやったかと、なぜ止めたかを残す**(CLAUDE.md か `docs/`)。
中途半端に見える状態が「意図的な線引き」だと分かるようにする。

## アンチパターン

| アンチパターン | なぜ悪いか |
| --- | --- |
| テストがない状態で動かし始める | 振る舞いが変わったか誰も分からない |
| リファクタリングと仕様変更を混ぜる | 壊した原因が特定できない |
| 全面書き直し(big bang) | 途中で力尽き、動かない新旧が両方残る |
| いきなり usecase 層だけ作る | 中身が空の層が増え、ロジックはモデルに残る |
| Django モデルを消してから作り直す | 動いていたものを失う。段階移行できない |
| 同じルールを新旧の両方に書く | 必ずズレる。旧から新へ委譲する |
| 書き込み経路を2つ残したまま進める | 不変条件が守れない |
| `XxxService` を `XxxDomainService` に改名して満足 | 貧血症は名前では直らない |
| 移行中に見つけた検索をリポジトリへ足す | リポジトリが Manager に逆戻りする |
| 支援・汎用サブドメインまで DDD 化する | 回収できないコストを払う |

## ルール(チェックリスト)

- [ ] 対象を**コアドメイン / よく壊れる箇所**に絞った。全面移行にしていない
- [ ] 着手前に**特性テスト**で現在の振る舞いを固定した(バグも含めて)
- [ ] リファクタリングと仕様変更を**別コミット**にしている
- [ ] **値オブジェクト → エンティティ → 集約 → リポジトリ → usecase** の順で進めている
- [ ] Django モデルを消さず、**委譲でつなぎながら**ロジックを移している
- [ ] 移す単位が**振る舞い1つ**。テストが緑になるたびにコミットしている
- [ ] エンティティを割るときは「同時に守る不変条件がない」ことを確認した
- [ ] `XxxService` の中身を**ルール / 手順 / 検索**に仕分けてから配った
- [ ] 同じ業務ルールが新旧に**二重実装されていない**
- [ ] **書き込み経路が一本**になっている
- [ ] 新旧の境界がファイル単位で明確。混在をファイル内に持ち込んでいない
- [ ] どこで止めるかを決め、止めた理由を残した
