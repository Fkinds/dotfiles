# 標準の定義に従う (Standards Compliance)

**形式・用語・挙動を自分で決める前に、標準が定義していないかを確かめる。** 定義があれば
それに従う。独自に決めた形式は、相手の実装やライブラリと噛み合わず、後から標準に寄せると
破壊的変更になる。

対象は、公開された標準文書に定義があるもの。IETF(RFC)、ISO / IEC、IEEE、W3C、WHATWG、
Ecma、IANA の登録簿、Unicode、NIST。OWASP のような推奨集は標準ではないので、ここでは扱わない。

---

## 1. 原則

1. **新しく決めるものは標準に従う。** 形式・名前・ステータス・用語の意味まで含む。
2. **既存の決まりと食い違ったら、黙ってどちらかに合わせない。** 第 2 節の形で報告し、
   どこまで直すかの判断を仰ぐ。頼まれていない範囲を標準に寄せて書き換えない。
3. **用語は標準の意味で使う。** 「冪等」「安全なメソッド」は RFC 9110 の意味、
   「MUST / SHOULD」は RFC 2119 / 8174 の意味。日常語の意味で使わない。
4. **標準が無い領域では、無いことを明記して決める**(第 5 節)。

---

## 2. 食い違いを報告する

既存のコード・ライブラリの既定・プロジェクトの規約が標準と違うときは、次の 4 点を書く。

| 項目 | 書くこと |
| --- | --- |
| 何が | 場所(`file:line`)と、今の形式や挙動 |
| どの標準と | 標準の番号と節(例: RFC 9457 3.1 節) |
| どう違うか | 標準ならどうなるか |
| 直すとしたら | 影響範囲(API の利用者、保存済みのデータ、互換性)。直さない選択肢も挙げる |

- フレームワークの既定が標準と違うことはよくある(DRF の既定のエラー形式と RFC 9457 など)。
  既定だからといって標準に沿っているとは限らない。
- 報告したうえで既存に合わせると決まったら、その決定に従う。同じ報告を繰り返さない。

### データの形式

| 領域 | 標準 | 要点 | 詳しくは |
| --- | --- | --- | --- |
| 日時・タイムゾーン | RFC 3339(RFC 9557 で更新)、ISO 8601、IANA tz database | 外へ出す日時は RFC 3339(ISO 8601 のプロファイル)で、オフセットを必ず付ける。RFC 9557 により、`Z` は「ローカルのオフセットは不明」、`+00:00` は「UTC が基準」を表す。期間は ISO 8601 の duration(`P1D`)。地域の時刻は `Asia/Tokyo` のような tz 名で持ち、`JST` のような略称や固定オフセットで代用しない | [ddd-modeling-primitives](../ddd-modeling-primitives/SKILL.md) |
| 金額・通貨 | ISO 4217、IEEE 754 | 通貨は 3 文字のコード。小数桁(minor unit)も ISO 4217 の表に従う(JPY 0、USD 2、BHD 3)。IEEE 754 の二進浮動小数点は 0.1 を正確に表せないので、金額に `float` を使わない | [ddd-modeling-primitives](../ddd-modeling-primitives/SKILL.md) |
| 識別子 | RFC 9562 | UUID の定義。RFC 4122 は廃止済み。時刻順に並べたいなら v7(v1 / v6 より v7 を使う)、順序が要らないなら v4 | [ddd-modeling-primitives](../ddd-modeling-primitives/SKILL.md) |
| 文字列 | Unicode、UTF-8(RFC 3629)、Unicode 正規化(UAX #15) | 外とやり取りする文字列は UTF-8。比較や一意性の判定の前に正規化形式を決める(既定は NFC。全角と半角を寄せるなら NFKC) | — |
| 国と言語 | ISO 3166-1、BCP 47 | 国は alpha-2(`JP`)。言語タグは BCP 47(`ja`、`ja-JP`)。独自の略称を作らない | — |
| URL・メールアドレス | RFC 3986、WHATWG URL Standard、RFC 5322 | URL は自前で分解せず、標準ライブラリのパーサに任せる。ブラウザの挙動は WHATWG、サーバー間の仕様は RFC 3986 が基準。メールアドレスは正規表現で厳密に判定しない。到達性は確認メールで確かめる | — |
| JSON・メディアタイプ | RFC 8259、IANA Media Types | JSON は UTF-8 で、BOM を付けない。整数が正確に一致するのは ±(2^53 − 1) の範囲までなので、それを超える ID や金額は文字列で渡す。`Content-Type` は登録済みの型を使い、独自なら `vnd.` 接頭辞 | — |

### 認証とセキュリティ

| 領域 | 標準 | 要点 | 詳しくは |
| --- | --- | --- | --- |
| 認証・セッション | RFC 6749 / 9700 / 7636、RFC 7519 / 8725、RFC 6265 | OAuth は Security BCP(RFC 9700)に従う。implicit grant は使わない(SHOULD NOT)、password grant は禁止(MUST NOT)。認可コードに PKCE を付け、方式は `S256`。JWT は検証側で許す `alg` を固定し、`none` を受け付けない(RFC 8725)。Cookie は `HttpOnly` / `Secure` を付ける。`SameSite` は RFC 6265 には無く、改訂版(6265bis、RFC 化の直前)で定義されている | [session-state-placement](../session-state-placement/SKILL.md) |

## 4. 現行版を確かめる

**確かめる場面**: 標準の番号や版を、ユーザーへの説明・コード・文書に書くとき。形式を新しく
決めるとき。それ以外の場面で毎回確かめる必要はない。

| 発行元 | 確かめ方 |
| --- | --- |
| IETF(RFC) | RFC Editor の info ページ(`https://www.rfc-editor.org/info/rfcNNNN`)で「Obsoleted by」「Updated by」と正誤表を見る。info ページは JavaScript で描画されるので、取得できなければ同じ内容の `https://www.rfc-editor.org/rfc/rfcNNNN.json` を見る。ドラフトは IETF Datatracker で状態と期限切れを見る |
| ISO / IEC | iso.org は機械的な取得を 403 で拒む。ISO Open Data の規格一覧(deliverables metadata)か、iso.org を対象にした検索結果で、版と段階を確かめる。段階コードは 60.60 が発行済み、90.92 が改訂の決定、90.93 が見直しのうえ維持、95.99 が廃止。一覧は約 20 MB で途中から再開できないので、取りに行くのは 1 回にとどめる |
| W3C | 版の URL ではなく「Latest version」の URL を見る。Recommendation か Draft かを確かめる |
| WHATWG | Living Standard なので常に最新が正 |
| NIST | SP の改訂番号(`-4` など)と、Final か Draft かを見る |
| IANA | 登録簿そのものを見る(tz database、Media Types) |
| Unicode | 最新の Unicode Standard と UAX の版を見る |

- **廃止された番号を書かない。** RFC 7807 → 9457、RFC 2616 / 7231 → 9110、RFC 4122 → 9562 のように
  番号が変わる。古い記事やライブラリのドキュメントは古い番号のまま残っている。
- 一次資料を確かめられなかったら、確かめていないことを明記して書く。

## 5. 標準が無いとき

1. 策定中のドラフトがあるか見る。**ドラフトは先取りで採用しない。** 仕様が変わると
   破壊的変更になる。デファクトで出しておき、標準になってから移す。
   例外は、主要な実装が出揃っているもの(Cookie の `SameSite` は主要ブラウザが実装済み)。
   実装に合わせて使い、ドラフトであることを書いておく。
2. デファクトの現物を見る(主要なライブラリの既定、Google AIP / Zalando などの公開ガイドライン、
   GitHub や Stripe の公開 API)。
3. 決めた形式と、**標準が無いこと**をコードか文書に書く。後から標準ができたときに
   移す対象が分かる。

Web API まわりの詳しい調べ方は [api-lifecycle](../api-lifecycle/SKILL.md) 第 5 節。

## アンチパターン

| アンチパターン | なぜ悪いか |
| --- | --- |
| 日時を `2026/11/04 10:00` のような独自形式で出す | 受け手ごとにパーサが要り、タイムゾーンが失われる |
| `JST` や `+09:00` 固定でタイムゾーンを表す | 夏時間のある地域や、オフセットの変わった歴史上の時刻を扱えない |
| 金額を `float` で持つ | 二進浮動小数点で端数がずれる |
| 通貨や国を独自の略称で持つ | 外部システムやライブラリと突き合わせられない |
| 廃止された RFC 番号を書く | 読み手が古い仕様を参照し、改訂で変わった点を見落とす |
| ドラフトのヘッダ名をそのまま本番に入れる | 標準化で名前が変わると破壊的変更になる |
| 既存の独自形式を黙って標準に書き換える | 利用者を壊す。食い違いは報告して判断を仰ぐ |
| フレームワークの既定を標準だと思い込む | 既定が標準と違うことはよくある |
