# skill-review

既存スキルを点検する。新規作成は [skill-authoring](../skill-authoring/SKILL.md)、
粒度の判断は [skill-scoping](../skill-scoping/SKILL.md)。

## 手順

1. 対象の `SKILL.md` をすべて読む。指定がなければ変更されたものを対象にする。

   ```bash
   git diff --name-only main...HEAD -- '**/SKILL.md'
   ```

2. 静的検査を先に通す。ここで落ちるものは指摘するまでもない。

   ```bash
   pre-commit run --all-files
   ```

3. 下記の検査項目を順に当てる。
4. **指摘は「どの行が」「なぜ問題で」「どう直すか」の 3 点セット**で出す。description の
   指摘には修正案の文面を書く。

## 検査項目

### A. frontmatter

- [ ] ファイル名が厳密に `SKILL.md`(`skill.md` は不可)。
- [ ] `name` が kebab-case で、**ディレクトリ名と一致**している。
- [ ] `description` がある。空でない。
- [ ] **配布先の制約**: claude.ai へのアップロード / Skills API / `package_skill.py` を通す
      なら、frontmatter は `name` / `description` / `license` / `compatibility` /
      `metadata` / `allowed-tools` の 6 つのみ。`user-invocable` や `argument-hint` が
      あると**ハードエラーでアップロードが失敗する**(無視されない)。Claude Code 専用と
      割り切るなら可。どちらの前提かを確認して指摘する。
- [ ] `allowed-tools` が過大でない。**プロジェクトにチェックインされたスキルは、そのターンの
      間 Claude に許可なしでツールを使わせる**。読むだけのスキルに `Write` / `Bash` は不要。
- [ ] YAML が壊れていない。壊れていると Claude Code はメタデータ空で本文だけを読み込み、
      `/名前` は動くのに**自動起動だけが静かに死ぬ**(`--debug` でパースエラーが見える)。

### B. description(起動精度)

- [ ] **What と When の両方**がある。何をするかだけ書いて、いつ使うかがない、が最頻の欠陥。
- [ ] **ユーザーが実際に口にする語**がトリガーとして入っている。実装者の語彙だけで書かれて
      いないか。
- [ ] 三人称で書かれている。
- [ ] 目的が 1 つ。「かつ」「〜も」で複数の目的が並んでいたら分割を提案する。
- [ ] 主要ユースケースが先頭にある。`description` + `when_to_use` は一覧上
      **1,536 文字**で切り詰められる。長い description は自分の末尾を失うだけでなく、
      一覧全体の文字数予算を食って**他スキルの description を丸ごと落とす**。
- [ ] 逆に広すぎないか。「コードを改善する」のような description は無関係な場面で起動する。

### C. 本文

- [ ] **500 行以下**。超えていたら補助ファイルへ逃がすか、スキルを分割する。
- [ ] **一度ロードされた本文はセッション中ずっと context に残る**前提で書かれているか。
      一度きりの手順のつもりで書かれた指示が、後続ターンで誤って効き続けないか。
- [ ] 「なぜ」「どういう経緯で」の説明が本文の大半を占めていないか。やることを書く。
- [ ] 毎回は要らない詳細(全オプション表、長い例の羅列、API 仕様)が本文に居座っていないか。
      → 補助ファイルへ。
- [ ] 補助ファイルがあるなら、`SKILL.md` から**何が書いてあっていつ読むか**が案内されて
      いるか。参照されていない補助ファイルは読まれない。
- [ ] 判断が要る箇所が表・チェックリストになっているか。散文の中に埋もれていないか。
- [ ] リンク切れがないか(相対パス、`${CLAUDE_SKILL_DIR}` の使い方)。

### D. 責務

- [ ] 1 スキル 1 ワークフローになっているか。詳細は
      [skill-scoping](../skill-scoping/SKILL.md)。
- [ ] CLAUDE.md に属する「事実」(技術スタック、ビルドコマンド)が紛れ込んでいないか。
- [ ] 他スキルと内容が重複していないか。重複はどちらが起動すべきかを曖昧にする。

### E. 起動制御

- [ ] **副作用のある手順**(デプロイ、コミット、外部への送信)に
      `disable-model-invocation: true` が付いているか。Claude に実行タイミングを
      決めさせてよい内容か。
- [ ] `user-invocable: false` が、ユーザーが直接起動しても意味をなさない背景知識にだけ
      使われているか。
- [ ] `context: fork` を使っているなら、会話履歴なしで成立する内容か(fork したサブ
      エージェントは会話履歴を持たない)。

## 症状別の処方

| 症状 | 原因 | 直し方 |
| --- | --- | --- |
| 起動しない | description にユーザーの語彙がない | トリガー語を追加。`when_to_use` に例示リクエストを足す |
| 起動しない(`/名前` は動く) | frontmatter の YAML 破損 | `--debug` でパースエラーを確認して修正 |
| 起動しない(スキルが多い) | 一覧の文字数予算を超えて description が落ちた | `/doctor` で寄与の大きいものを確認し、description を削る。低優先度のスキルを `skillOverrides` で `"name-only"` にする |
| 起動しすぎる | description が広すぎる | 対象と条件を具体化する。手動起動だけでよいなら `disable-model-invocation: true` |
| 起動するが出力が期待と違う | 本文の指示不足 | **新しいセッション**で再現する。書いた会話の残り文脈が指示不足を隠している |
| context を食う | 本文が長い / description が冗長 | 詳細を補助ファイルへ。`/context` の Skills 行と `/doctor` で実測する |

## 動作で確かめる

読むだけで終わらせない。疑わしい指摘は実際に確認する。

1. **新しいセッション**で、description に合う自然な言い方をして起動するか見る。
2. 起動すべきでない言い方でも試し、誤起動しないか見る。
3. 同じプロンプトを**スキルあり / なし**で流して差を見る。差がなければそのスキルは
   何も足していない。
4. 反復するなら `skill-creator` プラグインが起動率・出力・トークンを計測して比較する。

## 報告

- 落ちた検査項目を、深刻度順(起動しない > 誤起動 > 冗長 > 体裁)に並べる。
- description の指摘には**書き換え案の全文**を添える。
- 分割の提案は、どの軸で何と何に割るかまで書く。
- 問題がなければ「点検した項目」と「問題なし」を簡潔に伝える。指摘を作らない。
