# FSD: widgets レイヤー

**複数の feature / entity を束ねた、自己完結した UI ブロック。** レイヤーの選び方と
依存ルールは [fsd-layers](../fsd-layers/SKILL.md)。束ねる対象は
[fsd-features-layer](../fsd-features-layer/SKILL.md) /
[fsd-entities-layer](../fsd-entities-layer/SKILL.md)、置き先は
[fsd-pages-layer](../fsd-pages-layer/SKILL.md)。

**任意のレイヤー。** 無いまま運用しているプロジェクトは正常。

---

## 1. 作る条件

次の**両方**を満たすときだけ作る。

1. 複数の feature / entity を組み合わせている(1 つだけなら、それは feature か entity)。
2. **2 つ目のページでも同じ塊を使う**、または使うことが確定している。

1 つのページでしか使わない大きなブロックは、そのページの `ui/` に置く
(`pages/projects/ui/ProjectFilterPanel.tsx`)。**先に widget にしない。**

```text
widgets/project-table/
├── ui/
│   └── ProjectTable.tsx
├── model/          # 表示状態(並び順、開閉)がある場合のみ
└── index.ts
```

典型例: ヘッダー、サイドバー、検索フィルタ付きの一覧、ダッシュボードのパネル。

---

## 2. widget が持ってよいもの

| 持ってよい | 持たない |
| --- | --- |
| 配下の feature / entity の配置と組み合わせ | 業務ロジック(それは feature か entity) |
| ブロック内で閉じる表示状態(開閉、タブ、並び順) | ページ全体の状態、URL の状態 |
| 自分の表示に必要なデータ取得 | 他のブロックのためのデータ取得 |
| 自分の内部レイアウト | ページ上のどこに置かれるか(幅・余白は外が決める) |

### データ取得は自分でしてよい

widget が「自己完結」であるとは、**置くだけで動く**という意味。entity の
クエリを自分で呼んでよい。

- ただし取得したデータを**ページに返さない**。ページが必要とするなら、
  取得はページ側に移す。
- 同じデータを複数の widget が取ると重複するように見えるが、キャッシュを持つ
  データ取得ライブラリを使っていれば実際のリクエストは 1 回。**先回りして
  props バケツリレーにしない。**

### 何を props で受けるか

- 業務データそのものではなく、**どれを見るか**(`projectId`、フィルタ条件)を受ける。
- 表示の差し替え(空状態、ヘッダーの右端)は `ReactNode` の slot で開ける。

## 3. `pages/ui` との線引き

| 判断 | 置き場所 |
| --- | --- |
| 2 ページ以上で使う | `widgets/` |
| 1 ページ専用だが、そのページが長くなった | `pages/<page>/ui/` |
| ルート単位のレイアウト枠 | ルーティング側のレイアウト、または `app/` |
| 全ページ共通の外枠(ヘッダー、サイドバー) | `widgets/` に置き、`app` かレイアウトから使う |

**迷ったら `pages/<page>/ui/` に置く。** 2 つ目の利用者が現れたときに
`widgets/` へ引き上げるのは、import 元が 1 か所なので容易。

---

## 4. widget 同士は参照しない

同一レイヤーの cross-import は禁止。widget が他の widget を必要とするなら、
だいたい次のどれか。

| 状況 | 直し方 |
| --- | --- |
| 共通の見た目を使い回したい | `shared/ui` へ下ろす(業務語彙がないことを確認) |
| 一方が他方を内包する構造 | page で並べる。またはコンポジション(`children`)で外から差す |
| 実は 1 つのブロックだった | 1 スライスに統合する |

**入れ子にしたいときは props で受け取る。**

```typescript
// widgets/dashboard-panel/ui/DashboardPanel.tsx
type Props = { children: ReactNode };   // 中身は page が決める
```

## アンチパターン

| アンチパターン | なぜ悪いか |
| --- | --- |
| 1 ページでしか使わないブロックを widget にする | 使われないスライスが増え、遠くのファイルを読みに行くことになる |
| feature 1 つを包んだだけの widget | 層が 1 枚増えるだけで何も足していない |
| widget に業務ロジックを書く | feature / entity に置くべきものが、再利用できない位置に固定される |
| widget が取得したデータをページへ返す | 自己完結でなくなる。取得の責務がページと二重になる |
| 幅・余白・グリッド位置を widget 側で固定する | 置き場所によって崩れ、ページが調整できない |
| ページ全体の状態や URL の状態を widget が持つ | ブロックを別のページに置けなくなる |
| widget 同士を import する | 独立して削除・移動できなくなる |
| 「いつか使い回すはず」で先に widget を作る | 実際の 2 つ目が来ると要件が違い、作り直しになる |

---

## ルール(チェックリスト)

- [ ] **複数**の feature / entity を束ねているか(1 つだけを包んでいないか)
- [ ] **2 ページ目の利用者**が実在するか。しないなら `pages/<page>/ui/` に置いたか
- [ ] 業務ロジックを持たず、配置と組み合わせに徹しているか
- [ ] 持っている状態がブロック内で閉じているか(ページ全体・URL の状態でないか)
- [ ] 取得したデータをページへ返していないか
- [ ] props で受けているのは業務データではなく「どれを見るか」か
- [ ] 幅・余白などページ上の配置を自分で固定していないか
- [ ] 他の widget を import していないか(入れ子は `children` で受けているか)
