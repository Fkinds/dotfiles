# 一覧・流量・再送の取り決め (API Reliability)

**クライアントは必ず「たくさん」「もう一度」呼ぶ。** 一覧の返し方、流量の抑え方、
再送の受け止め方は、そのための取り決めとして先に決める。

エラーの形式は
[http-error-response](../http-error-response/SKILL.md)、
バージョニングと廃止は
[api-lifecycle](../api-lifecycle/SKILL.md)、
呼び出す側のリトライ・タイムアウトの置き場所は
[adapter-design](../adapter-design/SKILL.md)、
結果が不明なときの扱いは
[operation-result-design](../operation-result-design/SKILL.md)。

## 1. ページネーションはカーソル方式

**標準仕様はない。** GitHub / Stripe のデファクトはカーソル方式で揃っている。

```http
GET /v1/orders?limit=50&starting_after=ord_01H8X...
```

| | オフセット(`?page=3`) | **カーソル**(`?starting_after=...`) |
| --- | --- | --- |
| 途中で件数が変わったとき | **重複・取りこぼしが出る** | 出ない |
| 深いページ | `OFFSET` が線形に遅くなる | インデックスで直接飛べる |
| 任意のページへジャンプ | できる | できない |
| 総件数の表示 | 出しやすい | 別途数える必要がある |

- **既定はカーソル。** オフセットは「管理画面でページ番号を出したい」など、
  ジャンプが要件のときだけ。
- **カーソルは不透明な文字列**として扱わせる。中身(ID やソートキー)を
  仕様に書くと、変えられなくなる。
- **並び順を安定させる。** ソートキーが重複しうるなら、**一意なキーを最後に足す**
  (`created_at DESC, id DESC`)。同値があると境界で取りこぼす。
- **`limit` に上限を設ける**(既定 20〜50 / 最大 100 程度)。
  超えた指定はエラーにせず上限に丸めてよいが、どちらかを決めて明記する。
- **総件数を毎回返さない。** `COUNT` が一覧本体より重いことがある。要るときだけ。

### 次ページの伝え方

```http
Link: <https://api.example.com/v1/orders?starting_after=ord_01H9Z...>; rel="next"
```

- `Link` ヘッダ(RFC 8288)か、ボディに `next_cursor` / `has_more`。**どちらかに統一する。**
- **クライアントに URL を組み立てさせない。** 次ページの URL をこちらが返す。
- 最終ページでは `rel="next"` を**出さない**。空文字や `null` で判断させない。

## 2. レートリミット

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 30
X-RateLimit-Limit: 1000
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1735689600
```

- **超過は 429**(RFC 6585)。403 や 503 で代用しない。
- **`Retry-After` を必ず付ける。** これがないとクライアントは即座に再試行し、
  事態を悪化させる。秒数か HTTP-date。
- **残量ヘッダは標準がない。** 現状のデファクトは `X-RateLimit-Limit` /
  `-Remaining` / `-Reset`。IETF httpapi WG が `RateLimit` / `RateLimit-Policy`
  (Structured Fields)を策定中だが**まだ RFC ではない**ので、先取りしない
  ([api-lifecycle](../api-lifecycle/SKILL.md) の「標準がない領域の調べ方」)。
- 新規に `X-` 接頭辞を**発明しない**(RFC 6648)。既存デファクトの踏襲は別。
- **429 を返す前に、正常時から残量を返す。** 超過してから知らせても遅い。
- 制限の単位(利用者ごと / IP / エンドポイントごと)と窓の方式を決めて明記する。
- **書き込み系と読み取り系で別の制限にする。** 一括で絞ると読み取りが巻き添えになる。

## 3. 冪等キーで POST を再送可能にする

**タイムアウトは「失敗」ではなく「結果が不明」。** クライアントは再送するしかなく、
その結果が二重登録・二重決済になるのを止めるのがサーバ側の責任。

```http
POST /v1/payments
Idempotency-Key: 018f2b6e-...-a3d1
```

標準化ドラフトは期限切れで、**Stripe の実装が事実上の仕様**。踏襲する。

| 決めごと | 既定 |
| --- | --- |
| 対象 | **POST のみ**(GET/PUT/DELETE は元から冪等) |
| キーの形式 | クライアント生成の UUID v4 など。最大 255 文字 |
| 同じキーの再送 | **最初のリクエストの結果をそのまま返す**(再実行しない) |
| 保存期間 | 24 時間程度。過ぎたら別の要求として扱う |
| 同じキー・違うボディ | エラーにする(422 など)。別物として処理しない |
| 最初の処理が実行中 | 409 を返し、リトライさせる |

- **キーはクライアントが作る。** サーバが作るとリクエストと結びつかない。
- **リクエストのハッシュを一緒に保存する。** ボディ違いの取り違えを検出できる。
- **「保存 → 業務処理」を同一トランザクションに入れる。** 別々だと、
  記録前に落ちたときに二重実行される。
- **レスポンスも保存する。** 再送に対して同じ本文を返せないと意味がない。
- クライアントに要求するなら、**必須にするかどうかを明記する**。任意にすると
  誰も付けない。決済など二重実行が致命的な操作は必須にする。

## アンチパターン

| アンチパターン | なぜ悪いか |
| --- | --- |
| 一覧をオフセットで返す | 途中で件数が変わると重複・取りこぼしが出る |
| カーソルの中身を仕様として公開する | 内部のキーを変えられなくなる |
| ソートキーが重複しうるのに一意キーを足さない | 境界のレコードを取りこぼす |
| `limit` に上限を設けない | 1 リクエストで全件取られる |
| 毎回 `COUNT` して総件数を返す | 一覧本体より重くなる |
| 次ページの URL をクライアントに組み立てさせる | 仕様変更のたびに全クライアントが壊れる |
| 流量超過を 403 や 503 で返す | リトライしてよいか伝わらない |
| 429 に `Retry-After` を付けない | 即座に再試行され、事態が悪化する |
| 残量を超過時にしか返さない | 事前に減速できない |
| 策定中の `RateLimit-*` を先取りで採用する | 仕様変更が破壊的変更になる |
| 冪等キーを受けるが実行中の重複を弾かない | 同時到達した再送が二重実行される |
| 冪等キーの記録と業務処理を別トランザクションにする | 記録前に落ちると二重実行される |
| レスポンスを保存せず、再送時に再計算する | 同じ結果を返せない |
| 同じキーで違うボディを受け付ける | 別の要求が前の結果で上書きされる |

## ルール(チェックリスト)

- [ ] 一覧が**カーソル方式**(オフセットはジャンプが要件のときだけ)
- [ ] カーソルを不透明な文字列として扱わせている
- [ ] 並び順に**一意なキー**が入っていて、境界で取りこぼさない
- [ ] `limit` に既定値と上限があり、超過時の挙動を明記した
- [ ] 総件数を毎回は返していない
- [ ] 次ページの URL をサーバが返し、最終ページでは出していない
- [ ] 流量超過が **429** で、`Retry-After` が付いている
- [ ] 残量を正常時から返している
- [ ] 標準化中の `RateLimit-*` を先取りしていない / `X-` を新設していない
- [ ] 読み取り系と書き込み系で制限を分けている
- [ ] 二重実行が致命的な POST に **`Idempotency-Key`** を受け付けている
- [ ] キーの記録と業務処理が**同一トランザクション**
- [ ] レスポンス本文を保存し、再送に同じ結果を返している
- [ ] リクエストのハッシュを保存し、ボディ違いを検出している
- [ ] 実行中の重複到達を 409 で弾いている
- [ ] キーの保存期間を決めて明記した
