# 分散トランザクション戦略の選択

**どの戦略を選ぶか**に絞る。選んだ後の実装は各スキルに委ねる。

| 選んだもの | 実装を見る先 |
| --- | --- |
| 単一 DB 内のトランザクション境界 | [ddd-aggregate-repository-boundary](../ddd-aggregate-repository-boundary/SKILL.md) |
| サーガ(調整役・補償・タイムアウト) | [ddd-long-running-process](../ddd-long-running-process/SKILL.md) |
| outbox・イベント定義・冪等ハンドラ | [ddd-domain-events](../ddd-domain-events/SKILL.md) |
| サービス境界そのものの見直し | [ddd-bounded-context](../ddd-bounded-context/SKILL.md) |

## 1. まず「分散させない」を検討する

**最も安い分散トランザクションは、存在しない分散トランザクション。**
戦略を選ぶ前に、分散が必然かを疑う。

- **境界が間違っていないか。** 常に一緒に変わるものが別サービスに分かれているなら、
  それは分割の失敗。同じサービス・同じ DB に戻せば通常のトランザクションで済む。
- **本当に別 DB か。** 同一 DB の別テーブルなら分散ではない。単一トランザクションで足りる。
- **同期である必要があるか。** 呼び出し元が結果を待つ必要がなければ、多くは
  ドメインイベントで済む。

**マイクロサービスに分けてから 2PC で縫い合わせる**のは最悪の組み合わせ
(分散モノリス)。分割の利点を失い、複雑さだけが残る。

---

## 2. 一貫性の要求を測る

「強い一貫性が必要」は、たいてい検証されていない前提。次の 3 つで測る。

| 問い | 結果整合でよい兆候 |
| --- | --- |
| **不整合が観測されてよい時間窓は?** | 秒〜分で許される |
| **不整合が起きたとき誰がどう是正するか?** | 自動補償できる / 既に運用でカバーしている |
| **業務は今どう回っているか?** | 日次バッチで突合している = **すでに結果整合を受け入れている** |

3 番目が効く。既存業務が夜間バッチや翌日締めで整合を取っているなら、
システムだけ即時整合にする理由はない。

**強い一貫性が本当に要るのは**、不整合が瞬間でも観測されると法的・金銭的に損害が
出る場合(二重引き落とし、残高のマイナス、座席の二重販売)。それでも「予約 →
確定」の 2 段にできれば結果整合で組める(→ TCC)。

同じ問いは**単一サービス内で集約を切るときにも使う**。分散の有無に関わらず、
不変条件ごとに遅延可否を決める
([ddd-aggregate-repository-boundary](../ddd-aggregate-repository-boundary/SKILL.md))。

## 3. 戦略の選択

| 要件 | 戦略 | 代償 |
| --- | --- | --- |
| 強い一貫性・参加者が少数・同一組織内・低スループット | **2PC** | 可用性が全参加者の積になる。ロック保持。スケールしない |
| 強い一貫性・HTTP API 越し・異種 DB・「予約」が業務概念として自然 | **TCC** | 各サービスに 3 つの API。実装コスト約 3 倍 |
| イベント駆動・高可用性・スケーラビリティ | **サーガ** | 中間状態が観測される。補償の設計が必要 |
| 上記いずれでも、メッセージを失わないこと | **outbox**(+ CDC リレー) | インフラの追加。at-least-once |
| 既存レガシー DB からアプリを改修せず変更を取り出す | **CDC** | 行の変化しか分からない。意味が貧しい |

**サーガが既定値**。2PC / TCC は「結果整合では業務が成立しない」と示せたときだけ選ぶ。

---

## 4. 2PC (Two-Phase Commit)

コーディネータが全参加者に `prepare` を出し、全員が合意したら `commit` を出す。

**選べる条件**が厳しい。

- XA 対応のリソースマネージャ(DB、メッセージブローカ)であること。
- 参加者が少数(2〜3)、同一データセンター、低レイテンシ。
- スループットが低い。

**代償**:

- **可用性が参加者の積になる。** 各 99.9% の 3 参加者で 99.7%。参加者が増えるほど落ちる。
- **prepare から commit までロックを保持する。** ネットワーク遅延がそのままロック時間。
- **コーディネータが単一障害点。** 落ちると参加者が in-doubt のまま固まる。
- HTTP API 越しのサービスには使えない。

**実務**: Python / Django で XA を使うことは稀。多くの現場で 2PC は選択肢に入らず、
検討の結果として「使わない」と記録するための項目になる。

---

## 5. TCC (Try-Confirm/Cancel)

各サービスが 3 つの操作を公開する。**DB のロックの代わりに、業務上の「予約」状態を
アプリ層で持つ**のが本質。

| 操作 | 意味 |
| --- | --- |
| **Try** | リソースを予約する。まだ確定しない |
| **Confirm** | 予約を確定する。必ず成功しなければならない |
| **Cancel** | 予約を解放する。必ず成功しなければならない |

```python
class SeatReservation(Protocol):
    def try_reserve(self, tx_id: TxId, seat_id: SeatId) -> None: ...
    def confirm(self, tx_id: TxId) -> None: ...
    def cancel(self, tx_id: TxId) -> None: ...
```

- **Confirm / Cancel は失敗が許されない。** 外部要因で失敗しうる処理を Confirm に
  入れない。Try の時点で必要な資源をすべて確保しておく。
- **3 つとも冪等**でなければならない。`tx_id` で処理済みを判定する。
- **空の Cancel と、順序逆転**に備える。Try が届く前に Cancel が来ることがある
  (タイムアウトによる)。Cancel は「Try が無かった」場合も成功しなければならない。
- Try したまま Confirm も Cancel も来ない予約が残る。**期限切れで自動解放**する仕組みが要る。

**選ぶ場面**: 強い一貫性が要るが 2PC が使えない。かつ「予約 → 確定」が業務概念として
自然(座席、在庫引当、与信枠)。**自然でないなら TCC は無理筋**で、実装コストに見合わない。

---

## 6. サーガ

各ステップをローカルトランザクションで確定し、失敗したら**補償**で打ち消す。
実装(調整役の設計、補償の順序、タイムアウト、手動介入の導線)は
[ddd-long-running-process](../ddd-long-running-process/SKILL.md)。ここでは
**選べるかどうか**だけを判定する。

| 確認すること | 満たせない場合 |
| --- | --- |
| すべてのステップが**補償可能**か | 打ち消せない操作(送信・出金・出荷)が中核にあるなら、TCC の予約に置き換えられるかを先に検討する |
| **中間状態が業務的に見えてよい**か | 「注文は成立したが在庫は未引当」が画面・帳票に出て困るなら、強い一貫性側へ倒す |
| 補償の失敗を**人が拾える**体制があるか | 無いならサーガの運用は成立しない |

---

## 7. メッセージを失わない: outbox と CDC

「DB は更新できたがイベントを publish する前に落ちた」を防ぐ仕組み。**どちらも
at-least-once** であり、exactly-once にはならない。

| | outbox | CDC (Change Data Capture) |
| --- | --- | --- |
| 仕組み | アプリが業務データと**同じトランザクション**で outbox テーブルに書く。リレーが読んで配送 | DB のトランザクションログ(WAL / binlog)を読んで変更を取り出す |
| アプリの改修 | 必要 | **不要** |
| イベントの意味 | **業務上の出来事**を書ける(`OrderCancelled`) | **行の変化**しか分からない(`orders.status: 1 → 3`) |
| レガシーへの適用 | 難しい(コード改修が要る) | **容易** |
| 運用 | テーブルとリレーの管理 | Debezium 等の基盤とスキーマ変更の追従 |

### CDC の罠

**行の変化をそのままドメインイベントとして公開しない。** 何が起きたのかが失われ、
CRUD イベント(`OrderUpdated`)になる。受信側が「今回は何が変わったのか」を推測する
羽目になり、送信側のテーブル構造に結合する
([ddd-domain-events](../ddd-domain-events/SKILL.md) のアンチパターン)。

**最も筋がよい組み合わせ**: アプリが outbox テーブルに業務イベントを書き、
**CDC でその outbox テーブルを読んで配送する**。意味のあるイベントと、
ポーリング不要の確実な配送を両立できる。

CDC 単独が正当化されるのは、**改修できないレガシー DB から変更を取り出す**場合。
その場合も、取り出した行変更を**そのまま公開せず**、意味のあるイベントへ翻訳する
腐敗防止層を挟む。

---

## 8. 重複と順序に備える

どの戦略でも **at-least-once** になる。受信側の設計で吸収する。

- **冪等キー**を持つ。処理済みの `event_id` / `tx_id` を記録して弾く。
- 結果が同じになる操作にする。「在庫を 3 減らす」ではなく「この注文の引当を 3 にする」。
- **順序は保証されない**前提で書く。パーティションキーを揃えれば同一キー内の順序は
  保てるが、キーをまたぐ順序は保てない。バージョンや発生時刻で古いメッセージを捨てる。

---

## 9. 組み合わせと移行

戦略はシステム全体で 1 つに統一しなくてよい。**業務の重要度ごとに変える**。

- 決済の確定だけ TCC、それ以外はサーガ、という混在は妥当。
- レガシーからの移行期は CDC で変更を取り出し、順次 outbox へ寄せる。
- 戦略を変えるコストは高い。**最初に「どこまで強い一貫性が要るか」を決める**ことが、
  後戻りを避ける唯一の方法。

## アンチパターン

| アンチパターン | なぜ悪いか |
| --- | --- |
| マイクロサービスに分けてから 2PC で縫い合わせる | 分散モノリス。分割の利点を失い複雑さだけ残る |
| 検証せずに「強い一貫性が必要」と決める | 既存業務が日次バッチで回っているのに過剰設計になる |
| 補償できない操作をサーガの途中に置く | 失敗しても戻せない。最後に置くか TCC の予約にする |
| TCC の Confirm / Cancel に失敗しうる処理を入れる | Confirm は必ず成功しなければならない。Try で資源を確保する |
| CDC の行変更をそのままイベントとして公開 | CRUD イベントになり意図が失われる。テーブル構造に結合する |
| exactly-once を前提に受信側を書く | どの戦略も at-least-once。重複で二重処理になる |
| 結果整合を選んだのに UI が即時反映を前提 | 「反映されていない」という問い合わせが運用を圧迫する |

## ルール(チェックリスト)

- [ ] **分散させない選択肢**を先に検討した(境界の見直し、同一 DB、非同期化)
- [ ] 一貫性の要求を**時間窓・是正手段・既存業務**の 3 点で測った
- [ ] 強い一貫性が要ると判断したなら、その根拠(法的・金銭的損害)を書き出せる
- [ ] サーガを既定値とし、2PC / TCC はそれで成立しないと示せたときだけ選んだ
- [ ] サーガなら、**すべてのステップが補償可能**で、中間状態が業務的に許容される
- [ ] TCC なら、Confirm / Cancel が失敗せず、3 操作が冪等で、予約の期限切れがある
- [ ] メッセージの欠落対策がある(outbox。CDC を使うなら outbox テーブルを読む形)
- [ ] CDC の行変更を**そのまま公開していない**(意味のあるイベントへ翻訳している)
- [ ] 受信側が **at-least-once** 前提で冪等に書かれ、順序を仮定していない
- [ ] 結果整合を選んだなら、UI と運用がそれを前提にしている
