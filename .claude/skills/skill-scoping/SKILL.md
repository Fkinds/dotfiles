# skill-scoping

スキルを「どこで切るか」を決める。作成手順そのものは
[skill-authoring](../skill-authoring/SKILL.md)、既存スキルの点検は
[skill-review](../skill-review/SKILL.md)。

**そもそもスキルではなくサブエージェントにすべきか**の判断は
[agent-authoring](../agent-authoring/SKILL.md) の冒頭。会話の文脈が要る作業はスキル、
文脈を隔離したい・ツールを縛りたい作業はサブエージェント。

## 原則: 1 スキル = 1 ワークフロー

**1 つのスキルは、1 つの description で言い切れる目的を 1 つだけ持つ。**
「〜と、〜と、〜をします」と書きたくなったら、その時点で分割の対象。

分割が効く理由は 3 つ。

1. **コンテキストの節約。** スキルは段階的開示で読み込まれる。無関係な指示が
   context を圧迫しない。
2. **起動精度。** Claude は description だけで起動を判断する。目的が混ざると
   description が曖昧になり、必要なときに起動せず、不要なときに起動する。
3. **組み合わせ。** Claude は複数スキルを同時にロードして併用できる。単一目的の
   部品にしておけば、状況に応じて自動で組み合わされる。

## 段階的開示の 3 層

どの情報をどの層に置くかが、そのまま粒度の設計になる。

| 層 | 中身 | 読み込まれるタイミング | 目安 |
| --- | --- | --- | --- |
| 1 | `name` + `description`(スキル一覧) | **常時**、全スキル分 | 短く。合計 1,536 文字で切り詰め |
| 2 | `SKILL.md` 本文 | そのスキルが起動されたとき | 500 行以下 |
| 3 | 補助ファイル(`reference.md` / `examples.md` / `scripts/`) | 本文の指示で必要になったとき | 制限なし |

層 1 は全スキル分が常に載るので、**description の冗長さは他スキルの起動精度も削る**
(一覧の文字数予算を超えると、使用頻度の低いスキルから description が丸ごと落ちる)。

層 2 は一度ロードされるとセッション中ずっと残る。**「起動されたら最後まで居座る量」**として
妥当かで判断する。

層 3 は読まれるまでコストがゼロ。長い参照資料はここへ置く。

## 分割の判断

### 別スキルに割るサイン

- description に「かつ」「または」「〜も」が要る。目的が 2 つ以上ある。
- **起動条件が違う。** 片方は毎回の編集後、片方は PR 前だけ、など。
- **片方だけ使う場面がある。** 一緒に使われることが稀なら、パスを分けるだけでトークンが減る。
- 手順の前半と後半で、必要な知識がまったく重ならない。
- 一部だけ `disable-model-invocation` にしたい / `allowed-tools` を変えたい。
  frontmatter はスキル単位なので、粒度が合っていない証拠。

### 補助ファイルに逃がすサイン(スキルは割らない)

- 目的は 1 つだが本文が長い。特に、**毎回は要らない詳細**(全オプション表、API 仕様、
  例のバリエーション、長いテンプレート)が大半を占める。
- 実行するだけで読む必要のないスクリプト → `scripts/` へ。context に載らない。
- `SKILL.md` が 500 行を超えた。

判定: **「起動のたびに必ず要るか」**。必ず要るなら本文、条件付きなら補助ファイル。

### 分けすぎのサイン(統合する)

- 単独では意味をなさず、常に別のスキルと一緒に使われる。
- description の書き分けが苦しく、どちらが起動すべきか自分でも説明できない。
- 本文が数十行しかなく、片方の 1 セクションで足りる。

## 割り方の軸

同じ内容でも、切る軸で使い勝手が変わる。**起動条件が変わる線**で切る。

| 軸 | 例 | 向き |
| --- | --- | --- |
| **ワークフローの段階** | 設計 / 実装 / レビュー | 良い。段階ごとに起動条件が違う |
| **成果物の種類** | バックエンド / フロントエンド | 良い。触るファイルで切り分けられる(`paths` とも相性が良い) |
| **起動タイミング** | 編集直後の lint / PR 前のレビュー | 良い |
| 技術の細目 | ruff / mypy / black | 悪い。過剰分割。1 つの「lint する」に入る |
| 抽象度 | 概要 / 詳細 | 悪い。それはスキル分割ではなく層 2 / 層 3 の分け方 |

## 具体例

「Python コードの品質を保つ」を割る場合。

```text
NG(1 つに詰め込む):
  python-quality/SKILL.md
    → lint も型チェックもテストの書き方も DDD の設計指針も入る。
      description が「Python の品質全般」になり、いつ起動すべきか決まらない。

NG(割りすぎ):
  run-ruff / run-mypy / run-black / ...
    → 常に一緒に使われる。1 つの「lint する」で足りる。

OK:
  python-linter/SKILL.md    … .py を編集した直後に、プロジェクトのリンターを実行して直す
  pytest-practices/SKILL.md … テストを書く/レビューするときの作法
  ddd-domain-object-completeness/
    ├── SKILL.md             … ドメイン層を設計・レビューするときの指針
    └── examples/            … 長い実装例(必要なときだけ読む)
```

3 つとも起動条件が違い、単独でも成立し、必要なら併用される。

## チェックリスト

- [ ] description を 1 文で書けるか。「かつ」が要るなら割る
- [ ] 起動条件が 1 つに定まるか。タイミングが違うものが混ざっていないか
- [ ] 単独で使う場面があるか。常に他スキルとセットなら統合する
- [ ] 本文は「起動のたびに必ず要る」ものだけか。条件付きの詳細は補助ファイルへ
- [ ] `SKILL.md` が 500 行以下か
- [ ] 割った軸は「起動条件が変わる線」か(技術の細目や抽象度で割っていないか)
