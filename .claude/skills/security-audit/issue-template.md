# Issue の書式

`security-auditor` の報告の各指摘を、次の形に写す。報告では `####` だった見出しを `##` に上げ、
冒頭の区分・分類・関連は末尾の「分類」にまとめ、該当箇所はコミット SHA で固定したリンクに直す。

## タイトル

- 脆弱性: 何が起きるか(例:「LSP の TCP / WebSocket モードに認証がなく、ファイルの読み取りとコード実行ができる」)
- 強化と情報: 今どういう状態か(例:「GitHub Actions をコミット SHA で固定していない」)

## 本文

```markdown
## 概要

<何が問題か。仕組みを 2〜4 文で>

## 影響を受ける条件

- <どんな使い方・配置のときに問題になるか>

## 再現手順

再現済み(<確認したときのライブラリなどの版>)/ 未再現(<理由。コードを読んだ上での判断>)

<最小限の手順。値はダミー>

## 該当箇所

- <そこに何があるか>: https://github.com/<owner>/<repo>/blob/<コミット SHA>/<パス>#L<開始>-L<終了>

## 対応案(方針は着手前に決める)

- <候補>
- 現状でも取れる回避策: <あれば>

## 分類

- 区分: 脆弱性 / 強化 / 情報
- CVSS v4.0: `<ベクタ(CVSS:4.0/AV:…/SA:…)>` <スコア> <定性評価>(脆弱性のときだけ。計算できなければ「未計算」)
- CWE-<番号>: <名前>(当てはまるものがあれば)

関連: #<番号>(<関係>)

点検日: <YYYY-MM-DD> / 対象コミット: <短い SHA>
```

## 書き方

- 該当箇所のリンクは、必ずコミット SHA で固定する。ブランチ名のリンクは、後の変更で行がずれる。
- 再現手順の値はダミーだけにする。本物の秘密値やトークンは書かない。
- 「関連」には、他の指摘の Issue に加えて、既存の Issue(依存の更新の運用など)も書く。関連が
  無ければ行ごと省く。
