# テスト設計技法 (Test Design Techniques)

**テストケースは思いつきで並べず、仕様から技法で導く。** 技法ごとに「何を網羅したら
終わりか」が決まっているので、何件書けば足りるかに答えが出る。抜けは技法の
カバレッジ基準と照らして見つけ、重複は同じ同値パーティションを 2 度試していないかで
見つける。

前提: pytest + Hypothesis。技法の名前・分類・カバレッジ基準は
ISO/IEC/IEEE 29119-4:2021 に、日本語は JSTQB の訳語に合わせる。準拠を主張するもの
ではなく、拠り所として使う。

どの層で何をテストするかは [ddd-testing-strategy](../ddd-testing-strategy/SKILL.md)、
テストの分類と実行は [test-harness](../test-harness/SKILL.md)、
遷移表からテストを生成する書き方は
[ddd-state-transition](../ddd-state-transition/SKILL.md) 第 7 節。
各技法の pytest / Hypothesis の実装例は [examples.md](examples.md)。

---

## 1. 技法を選ぶ

**仕様の形を見て選ぶ。** 1 つの関数に複数の技法を重ねてよい(むしろ普通)。

| 仕様にあるもの | 技法 | 29119-4 |
| --- | --- | --- |
| 値の範囲や種類で振る舞いが分かれる | 同値分割法 → 境界値分析 | 5.2.1 / 5.2.3 |
| 複数の条件の組み合わせで結果が決まる | デシジョンテーブルテスト | 5.2.6 |
| 状態があり、操作で状態が変わる | 状態遷移テスト | 5.2.8 |
| 独立したパラメータが多く、全組み合わせが爆発する | 組み合わせテスト(ペアワイズ) | 5.2.5 |
| どの入力でも成り立つ性質がある | ランダムテスト | 5.2.10 |
| 正しい出力を前もって計算できない | メタモルフィックテスト | 5.2.11 |
| 過去の不具合、型や題材にありがちな失敗 | エラー推測 | 5.4.1 |

進める順序:

1. **同値分割で入力と出力を分ける。** ほぼすべての関数で最初にやる。
2. 分けたパーティションに順序があれば、**境界値分析**で境界を足す。
3. 条件の組み合わせ・状態・多数のパラメータがあれば、表の該当する技法を重ねる。
4. **エラー推測**で、仕様からは出てこないケースを足す。
5. **ブランチカバレッジを測って抜けを探す**(第 10 節)。抜けがあれば仕様に戻って
   同値パーティションを見直す。コードの分岐から逆算してケースを作らない。

## 2. 同値分割法 (equivalence partitioning, 5.2.1)

**同じ扱いをされる値の集まり(同値パーティション)に分け、各パーティションから
代表を 1 つ選ぶ。**

- **有効パーティションと無効パーティションの両方**を作る。無効パーティションは
  「拒否されるべき入力」の集まり。
- **出力側も分ける。** 「割引なし / 割引あり / 送料無料」のように結果が分かれるなら、
  各結果に到達する入力が要る。
- **分ける根拠は仕様。** 型(`int` / `str`)で分けるのではなく、業務上の扱いで分ける。

**カバレッジ基準**: すべての同値パーティションを少なくとも 1 回試す。パラメータが
複数あるなら、各パラメータのすべてのパーティションを少なくとも 1 回ずつ使う
(イーチチョイスカバレッジ)。

- **無効パーティションは 1 ケースに 1 つだけ入れる。** 2 つ混ぜると、先に検査された方で
  弾かれ、もう一方の検査が実際に働いているかが分からない(欠陥のマスキング)。
- 有効パーティションは 1 ケースにまとめてよい。

## 3. 境界値分析 (boundary value analysis, 5.2.3)

**順序のある同値パーティションの端を試す。** 不具合は `<` と `<=` の取り違えのように、
パーティションの境目に集まる。順序のないパーティション(色、支払い方法)には使えない。

| 方式 | 境界ごとに選ぶ値 | 見つけられるもの |
| --- | --- | --- |
| 2 値 | 境界値と、隣のパーティションで最も近い値 | 比較演算子の取り違え |
| 3 値 | 境界値と、その両隣 | 上に加え、`<=` が `==` になっている等 |

**カバレッジ基準**: 選んだ方式で、すべての境界値を試す。

- **既定は 2 値。** 金額・日時・閾値のように境界そのものが業務ルールなら 3 値にする。
- **「隣」は値の刻みで決まる。** 整数なら ±1、円なら ±1 円、`Decimal("0.01")` 刻みなら
  ±0.01、日付なら ±1 日。刻みが決まらない(float の連続値)なら、仕様で刻みを決めてから
  境界を取る。
- **仕様の境界を取る。** コードの `if` の境界ではない。両者が違えば、それが不具合。
- **0・空・`None` は境界値ではない。** 仕様に「1 件以上」とあれば 0 は境界の隣だが、
  そうでなければそれはエラー推測(第 9 節)のケース。

## 4. デシジョンテーブルテスト (decision table testing, 5.2.6)

**条件の組み合わせと、そのときの動作を表にし、表の列(規則)を 1 件ずつ試す。**

1. 条件(会員か、合計 5,000 円以上か、離島か)と動作(送料無料、送料加算)を挙げる。
2. 条件の真偽の組み合わせを列に並べ、各列の動作を**業務に確認して**埋める。
3. 結果が変わらない条件は「-」(どちらでもよい)にして列を畳む。
4. あり得ない組み合わせの列は消し、**消した理由を表の外に書く**。

**カバレッジ基準**: 実行可能な列をすべて試す。

- 表そのものを `parametrize` の並びとして書く(第 11 節)。表とテストが 1 対 1 になり、
  列の追加漏れがテストの差分で見える。
- 条件が多くて列が爆発するなら、条件同士が独立かを疑う。独立なら組み合わせテスト
  (第 6 節)の領域。

## 5. 状態遷移テスト (state transition testing, 5.2.8)

**状態・イベント・遷移(とガード条件)をモデルにし、遷移を試す。**
DDD の集約なら、遷移表がそのままモデルになる
([ddd-state-transition](../ddd-state-transition/SKILL.md))。

| カバレッジ基準 | 試すもの | 強さ |
| --- | --- | --- |
| 全状態カバレッジ | すべての状態に 1 度は到達する | 弱い。遷移の抜けを見逃す |
| 有効遷移カバレッジ(0 スイッチ) | 許可された遷移をすべて 1 度通る | 中 |
| 全遷移カバレッジ | 有効遷移に加え、**無効な遷移をすべて試して拒否される**ことを確かめる | 強い |

- **既定は全遷移カバレッジ。** 不正な遷移が止まることこそ守りたい性質で、許可された
  遷移は実装で自然に通る。`ddd-state-transition` 第 7 節の、遷移表から全ペアを
  生成する書き方はこの基準を満たす。
- **無効な遷移は 1 ケースに 1 つ。** 続けて試すと、最初の無効な遷移が誤って通った
  ときに状態が変わり、後の試行が想定と違う状態から行われる(欠陥のマスキング)。
- 遷移の**並び**(承認 → 差し戻し → 再申請)に不具合が出るなら、連続する遷移を試す。
  手で並べず Hypothesis のステートフルテストに生成させる([examples.md](examples.md))。

## 6. 組み合わせテスト (combinatorial testing, 5.2.5)

**独立したパラメータが多いとき、全組み合わせではなく決めた強さで組み合わせを選ぶ。**

| 方式 | 選び方 | 件数の目安(4 値 × 4 パラメータ) |
| --- | --- | --- |
| 全組み合わせ | すべて | 256 |
| ペアワイズ | **任意の 2 パラメータの値の組**がどこかで 1 度は現れる | 16 前後 |
| イーチチョイス | 各パラメータの各値が 1 度は現れる | 4 |
| ベースチョイス | 基準の組から 1 パラメータずつ変える | 13 |

- **既定はペアワイズ。** パラメータ同士の相互作用を 2 つ組まで押さえつつ、件数が
  パラメータ数に対してほぼ増えない。生成は `allpairspy` に任せる。手で作らない。
- **あり得ない組は、モデルを分けて避ける。** 「JSON にはヘッダ行がない」なら、
  表形式の組と JSON の組を別々に生成して足し合わせる。生成後に行を手で消すと、
  その行にしか無かったペアが消える。
- **`allpairspy` の `filter_func` で制約を渡すと、ペアを取りこぼす**ことがある
  (4 パラメータ 36 通りで実測し、1 ペア落ちた)。どちらの方法でも、
  **生成した組があり得るペアをすべて含むことをテストで確かめる**。
- 各パラメータの値は、先に**同値分割で代表値に絞ってから**入れる。生の値を並べると
  件数が膨らむ。

## 7. ランダムテスト (random testing, 5.2.10)

**入力を生成器から大量に作り、すべての入力で成り立つ性質を確かめる。**
期待値を 1 件ずつ書かない代わりに、**何を正しさとするか(テストオラクル)を性質で書く。**

使える性質:

- **往復**: `decode(encode(x)) == x`。シリアライザ、リポジトリのマッピング。
- **不変条件**: 生成したどんな入力でも、結果が不変条件を満たす(合計が一致する、
  並びが昇順になる)。
- **例外の種類**: 妥当な入力なら例外が出ない。無効な入力ならドメイン例外だけが出る。
- **別実装との一致**: 遅いが明らかに正しい実装と結果が一致する。

- **境界は `@example` で固定する。** Hypothesis は端の値を出しやすいが、出る保証はない。
  境界値分析で導いた値は明示する。
- **テストの中で実装と同じ計算をしない。** 同じ誤りをテストも共有し、必ず通る。
- **性質だけで済ませない。** 性質は「どの値になるか」を言わない(按分の合計が
  合っていても、端数の行き先は確かめていない)。業務ルールで決まる具体的な値は、
  通常のテストで書く。
- 生成器(strategy)は**有効パーティションだけを作る**ように組む。無効な入力は
  別のテストに分ける(第 2 節のマスキングと同じ理由)。

## 8. メタモルフィックテスト (metamorphic testing, 5.2.11)

**個々の正解は分からなくても、入力をこう変えたら出力はこう変わる、という関係
(メタモルフィック関係)は分かる。** その関係を確かめる。

| 対象 | メタモルフィック関係 |
| --- | --- |
| 検索・絞り込み | 条件を足すと、結果は元の結果の部分集合になる |
| 按分 | 比率をすべて k 倍しても、配分結果は変わらない |
| 集計 | 入力の並びを入れ替えても、合計は変わらない |
| 経路・最適化 | 制約を緩めると、最適値は悪くならない |

- 正解を手で計算できない処理(最適化、統計、複雑な料金計算)に使う。
- 入力の元の組は Hypothesis に生成させ、変換後の入力と出力の関係だけを書く。
- 関係は**業務の言葉で言えるもの**にする。言えない関係は、仕様の誤解を固定しやすい。

## 9. エラー推測 (error guessing, 5.4.1)

**仕様からは出てこないが、経験上よく壊れるケースを足す。** 仕様ベースの技法の後に
やる。先にやると、思いつきのケースだけで満足してカバレッジ基準を確かめなくなる。

| 題材 | よく壊れるケース |
| --- | --- |
| 数値 | 0、負値、上限、`Decimal` と `float` の混在、丸めの境目(0.5) |
| 文字列 | 空、空白だけ、最大長、絵文字や結合文字、全角と半角 |
| コレクション | 空、1 件、重複、順序に依存する処理 |
| 日時 | 月末、閏日、タイムゾーンの変わり目、naive と aware の混在 |
| 外部入力 | `None`、型違い、余分なキー、欠けたキー |

- **想定される誤りを先に並べてから、1 つずつ試す。** JSTQB はこのやり方を
  フォールト攻撃と呼ぶ。思いつくたびに試すより漏れが減る。
- 上の表は出発点。**プロジェクトで出た不具合の種類を足していく。** エラー推測の質は、
  過去の不具合をどれだけ覚えているかで決まる。
- 日時と金額の題材ごとの落とし穴は
  [ddd-modeling-primitives](../ddd-modeling-primitives/SKILL.md)。

## 10. カバレッジで抜けを測る (statement / branch testing, 5.3.1 / 5.3.2)

**構造ベースの技法はケースを導くためではなく、抜けを見つけるためだけに使う。**

```bash
pytest --cov=<package> --cov-branch --cov-report=term-missing
```

- **ブランチカバレッジで測る。** ブランチを 100% 通せばステートメントも 100% になるが、
  逆は成り立たない(`if` の偽側を通らなくても全行は実行できる)。
- **通っていない分岐を見つけたら、仕様に戻る。** その分岐に対応する同値
  パーティションやデシジョンテーブルの列が抜けている。分岐を通すためだけの入力を
  作らない。
- **数値を目標にしない。** 目標にした途端、検証のないテストで数値が埋まる
  ([ddd-testing-strategy](../ddd-testing-strategy/SKILL.md) 第 7 節)。

## 11. 導いたケースをテストに残す

文書は作らない。**テストを読めば、どの技法で何を網羅したかが分かる**ようにする。

- **テスト名に技法の単位を入れる。** 同値パーティション、境界、表の列、遷移の名前。
- **`pytest.param(..., id=...)` に境界の意味を書く。** `id="大人の下限(13)"`。
  数字だけの id はどの境界かが読めない。
- **デシジョンテーブルは表のまま並べる。** 1 行 1 列(規則)。列の名前を id にする。
- **正常系と異常系の `parametrize` を分ける**
  ([ddd-testing-strategy](../ddd-testing-strategy/SKILL.md) 第 2 節)。

```python
@pytest.mark.parametrize(
    ("age", "expected"),
    [
        pytest.param(0, FareCategory.CHILD, id="子供の下限(0)"),
        pytest.param(12, FareCategory.CHILD, id="子供の上限(12)"),
        pytest.param(13, FareCategory.ADULT, id="大人の下限(13)"),
        pytest.param(64, FareCategory.ADULT, id="大人の上限(64)"),
        pytest.param(65, FareCategory.SENIOR, id="シニアの下限(65)"),
    ],
)
def test_年齢の境界で区分が切り替わる(age: int, expected: FareCategory) -> None:
    assert fare_category(age) is expected
```

## 採らない技法

29119-4 の技法のうち、次は採らない。必要になった案件では個別に足す。

| 29119-4 | 技法 | 採らない理由 |
| --- | --- | --- |
| 5.2.2 | クラシフィケーションツリー技法 | 同値分割と組み合わせテストで足りる。木を描く道具が前提 |
| 5.2.4 | 構文テスト(syntax testing) | パーサや DSL を作るときだけ要る |
| 5.2.7 | 原因結果グラフ(cause-effect graphing) | デシジョンテーブルで足りる |
| 5.2.9 | シナリオベースドテスト | E2E や BDD の領域で、関数単位のケース導出とは別 |
| 5.2.12 | 要件ベースドテスト | 要件とテストの対応づけはプロセス側の話 |
| 5.3.3–5.3.7 | デシジョンテスト、ブランチ条件(組み合わせ)テスト、改良条件判定テスト(MC/DC)、データフローテスト | 航空などの安全規格向け。Python の測定道具も乏しい |

ミューテーションテストは 29119-4 の技法ではなく、テストの十分さを評価する手段なので
このスキルの範囲外。

## アンチパターン

| アンチパターン | なぜ悪いか |
| --- | --- |
| 思いついた値を並べて終わる | 何を網羅したかが言えず、抜けも重複も判断できない |
| 無効な値を 1 ケースに 2 つ入れる | 先に弾かれた方しか検査されない(マスキング) |
| 0・空・`None` を並べて「境界値テスト」と呼ぶ | 仕様の境界を試していない。それはエラー推測 |
| コードの `if` から境界を取る | 実装が仕様とずれていても、そのずれを固定する |
| 許可された遷移だけテストする | 不正な遷移が通る不具合を見逃す |
| 全組み合わせを手で並べる | 件数が爆発し、やがて誰も足さなくなる |
| ペアワイズの結果から手で行を消す | その行にしか無かったペアが消える。モデルを分ける |
| 生成したペアの網羅を確かめない | 道具が制約の扱いでペアを取りこぼしても気付かない |
| 性質のテストで実装と同じ計算をする | 同じ誤りを共有し、必ず通る |
| 境界値を Hypothesis の生成に任せる | 出る保証がない。`@example` で固定する |
| カバレッジを通すためだけの入力を足す | 仕様の抜けを埋めずに数値だけが上がる |
| id が数字だけの parametrize | どの境界・どの列を試したかが読めない |

## 規格との対応

- 技法の名前と節番号は **ISO/IEC/IEEE 29119-4:2021**(第 2 版)。本文は有料で、
  目次と用語定義はプレビューで読める。第 6 章が技法ごとのカバレッジの測り方。
- 用語と概念は **ISO/IEC/IEEE 29119-1:2022**。ISO が無償公開している
  (ライセンスへの同意が要る)。
- 日本語の訳語は **ISTQB 用語集の日本語版**。JSTQB は用語集を ISTQB のサイトに
  一本化している。
- カバレッジ基準の説明は **JSTQB Foundation Level シラバス v4.0**(同値分割法・境界値分析・
  デシジョンテーブル・状態遷移・ステートメント・ブランチ・エラー推測)と
  **Advanced Level テストアナリスト v4.0**(組み合わせテスト・ペアワイズ)。どちらも無償公開。
- JSTQB の訳語が無い技法(構文テスト、原因結果グラフによるテスト、ブランチ条件テスト)は、
  英語名を添えて書いている。
- ここに書いた規格の版と節番号は**執筆時点のスナップショット**。規格に基づくと
  説明する必要がある場面では、現行版を確かめる。
- テスト以外の領域の標準と、規格の現行版の確かめ方は
  [standards-compliance](../standards-compliance/SKILL.md)。

## ルール(チェックリスト)
