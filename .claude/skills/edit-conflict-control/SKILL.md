# 編集の競合を防ぐ (Offline Concurrency)

**読んでから書くまでの間に人が挟まる編集で、他の人の変更を黙って上書きしない。**
1 つのリクエストの中で起きる競合(読む → 変える → 保存する)は
[ddd-aggregate-repository-boundary](../ddd-aggregate-repository-boundary/SKILL.md) の
[concurrency.md](../ddd-aggregate-repository-boundary/concurrency.md) が扱う。ここは、
その間に**画面の表示とユーザーの思考時間**が入る場合を扱う。

出典は Martin Fowler『Patterns of Enterprise Application Architecture』の
Offline Concurrency Patterns。各パターンの要約は
[著者のカタログ](https://martinfowler.com/eaaCatalog/)にある。

関連スキル:

- エラーレスポンスの形(Problem Details) → [http-error-response](../http-error-response/SKILL.md)
- 同じ送信が 2 回届く問題(二重送信)は別の問題 → [api-reliability](../api-reliability/SKILL.md) の Idempotency-Key
- 仮押さえを状態として持つ → [ddd-state-transition](../ddd-state-transition/SKILL.md)

## 1. 何が起きるか

```text
10:00  A が予約 #42 の編集画面を開く(版 7 を読む)
10:01  B が予約 #42 の編集画面を開く(版 7 を読む)
10:03  B が人数を 4 → 5 に変えて保存する → 版 8
10:05  A が備考を書き足して保存する
```

10:05 の保存リクエストは、その場で予約 #42 を読み直す。読み直した版は 8 なので、
**リクエストの中の楽観的ロックは何も検出しない。** A の画面に残っていた「人数 4」が
保存され、B の変更が消える。

**防ぐには、A が読んだ版(7)を画面に持たせ、保存のリクエストで送り返させる。**

---

## 2. 方式の選び方

| 状況 | 方式 |
| --- | --- |
| 編集するのが実質 1 人(自分のプロフィール・自分の下書き) | **後勝ち**。何もしない |
| 複数人が編集しうる。衝突は稀で、やり直しが安い | **楽観的オフラインロック**(第 3 節)。**既定はこれ** |
| 入力に時間がかかり、衝突したときのやり直しが高い(長文・見積書・設定画面) | **悲観的オフラインロック**(第 6 節)+ 楽観的オフラインロック |
| 座席・在庫・担当など、**確保したこと自体に業務上の意味がある** | ロックではなく**業務の状態**として持つ(第 7 節) |

- **後勝ちは「選んだ」ときだけ許される。** 選んだ理由(編集者が 1 人)を書いておく。
  何もしていない状態とは区別する。
- **悲観的オフラインロックは単独で使わない。** 期限切れ・強制解除のあとに保存が届くので、
  楽観的オフラインロックを必ず重ねる。

---

## 3. 楽観的オフラインロック — 版を往復させる

1. **読み取りで版を返す。** API なら `ETag` ヘッダ、HTML フォームなら hidden の入力欄。
2. **更新で版を送り返させる。** API なら `If-Match` ヘッダ、フォームなら hidden の値。
3. **送り返された版を、条件付き UPDATE まで渡す。** サーバーが読み直した版を使わない。

```python
class UpdateReservation:
    def execute(self, command: UpdateReservationCommand) -> ReservationOutput:
        reservation = self._reservations.find_by_id(ReservationId(value=command.reservation_id))
        if reservation is None:
            raise ReservationNotFound(command.reservation_id)
        if reservation.version != command.expected_version:
            raise StaleVersion(current=reservation.version)      # 画面を開いた後に誰かが更新した
        updated = reservation.change_party_size(PartySize(value=command.party_size))
        self._reservations.save(updated)  # WHERE version = expected の条件付き UPDATE
        return ReservationOutput.from_domain(updated)
```

- 版の比較と保存の間に割り込まれた場合は、条件付き UPDATE が検出する
  (`ConcurrentModification`、[concurrency.md](../ddd-aggregate-repository-boundary/concurrency.md))。
  **どちらも「あなたの見ていた版は古い」という同じ意味**なので、同じ応答に変換する。
- **自動でリトライしない。** ユーザーが見ていない内容で上書きすることになる。
- 削除も同じ。`DELETE` にも版を要求する。

### HTTP での応答

| 場面 | ステータス |
| --- | --- |
| `If-Match` の版が古い | **412 Precondition Failed** |
| 版を必須にした更新で `If-Match` が無い | **428 Precondition Required** |
| `If-Match: *` | 受け付けない(428 と同じ扱い)。版を確かめない上書きになる |
| HTML フォームの hidden の版が古い | **409 Conflict**。入力を残したままフォームを再表示する |

応答の本文は Problem Details にし、最新の版と内容を返す
([http-error-response](../http-error-response/SKILL.md))。

### Django での注意

- **`ETag` は版から作り、比較は自前で行う。** 例: `ETag: "7"`。
- **圧縮が ETag を弱める。** `GZipMiddleware`(nginx の gzip も同様)は強い ETag に
  `W/` を付ける。クライアントはそれをそのまま `If-Match` に入れて送り返す。
- **Django の `condition` デコレータは `If-Match` を強い比較で判定する。** 弱い ETag は
  一致しないので、圧縮と組み合わせると**更新が常に 412** になる(Django 6.0 の
  `django/utils/cache.py` で確認)。412 の本文も Problem Details にならない。
- だから `If-Match` は自前で読み、`W/` と引用符を外して版の番号どうしで比べる。
  この ETag は表現のバイト列ではなく版の番号なので、それで意味が合う。

```python
def expected_version(request: Request) -> int:
    raw = request.headers.get("If-Match")
    if raw is None or raw.strip() == "*":
        raise PreconditionRequired()                      # → 428
    value = raw.strip().removeprefix("W/").strip('"')
    if not value.isdigit():
        raise ValidationError({"If-Match": "版の番号を指定してください"})
    return int(value)
```

## 4. ロックは集約の単位でかける

**版は集約ルートに 1 つ。** 子(注文明細)を編集するときも、送り返させるのは親の版。

- 明細を `/orders/1/lines/3` のように個別のリソースとして公開していても、その `ETag` は
  **注文の版**にする。明細ごとに版を持たせると、明細 A と明細 B の同時編集で
  「明細の合計は与信枠以内」のような集約の規則が破れる。
- 版を集約単位にすると、**関係のない部分の編集でも 412 になる。** 頻発するなら、集約が
  大きすぎるサイン([ddd-aggregate-repository-boundary](../ddd-aggregate-repository-boundary/SKILL.md) 第 3 節)。

## 5. かけ忘れを防ぐ

更新のエンドポイントを足すたびに版の確認を書く方式は、いつか 1 つ書き忘れる。
**確認を省略できない形にする。**

- **更新のコマンド DTO に `expected_version` を必須の項目として持たせる。** 既定値を付けない。
- **リポジトリの `save` が常に条件付き UPDATE を行う。** 版を確かめない保存の経路を作らない。
- **更新系の view が共通の部品(mixin や上の `expected_version`)を通る。** `PUT` / `PATCH` /
  `DELETE` で `If-Match` が無ければ 428。
- **テストで網羅を確かめる。** URL の一覧から更新系のエンドポイントを集め、`If-Match`
  なしで 428 になることを 1 本のテストで検査する。

## 6. 悲観的オフラインロック — 編集ロック

編集画面を開いた人だけが保存できるようにし、他の人には「A さんが編集中」と見せる。
**衝突してから気付く**のではなく、**編集を始める前に気付ける**のが利点。

- **DB のロック(`select_for_update`)やトランザクションを、リクエストをまたいで
  持ち越さない。** できないし、できても接続を握り続ける。ロックは**行として**記録する。
- **期限を必ず付ける。** ブラウザを閉じた人のロックは自分では外れない。編集中は
  画面から定期的に延長する。
- **保存の時点で、ロックが自分のものでまだ有効かを確かめる。** 期限切れで他の人に
  取られている可能性がある。そのうえで版も確かめる(第 3 節)。
- **強制解除の手段を用意する。** 管理者や、その記録の責任者が外せるようにする。
  外された側の保存は、保存時の確認で失敗する。
- 画面には**誰が・いつまで**ロックしているかを出す。

ロック表の定義、取得・延長・確認・解除の実装、期限の決め方、Redis に置く場合の
注意は [edit-lock.md](edit-lock.md)。編集ロックを入れると決めたときに読む。

## 7. 確保に業務上の意味があるなら、ロックではなく状態にする

座席の仮押さえ、在庫の引当、問い合わせの担当者決めは、技術的なロックに見えるが
**業務の事実**。

| | 技術的なロック | 業務の状態 |
| --- | --- | --- |
| 守るもの | 編集作業 | 業務の資源(座席・在庫・担当) |
| 見る人 | 編集しようとした人だけ | 業務の関係者全員。一覧や集計にも出る |
| 期限切れ | ロックが外れるだけ | **業務の出来事**(仮押さえの失効 → 席が空く、通知する) |
| 置き場所 | ロック表 | **集約の状態と遷移**([ddd-state-transition](../ddd-state-transition/SKILL.md)) |

- 「15 分以内に支払わないと仮押さえが外れる」は、`Hold` の状態と期限を持つ集約として
  書く。期限切れの処理もドメインの遷移にする。
- **確保そのものは 1 リクエストで終わらせる。** 「空席を見て → 確保する」を 2 回の
  リクエストに分けると、その間に埋まる。確保の操作が空きを確かめて確保までを一度に行う。

---

## 8. 競合したときの画面

- **ユーザーの入力を捨てない。** 412 / 409 を受けたら、入力内容を画面に残したまま、
  最新の内容を並べて見せる。
- **何が変わったかを示す。** 自分が読んだ版と最新版の差分を出せれば、ユーザーは
  入れ直すべき箇所だけを判断できる。
- **黙って自動マージしない。** フィールドが重なっていなくても、業務上は連動している
  ことがある(人数と料金)。
- 「上書きして保存」を出すなら、**最新の版を読んだうえでの上書き**にする。古い版のまま
  送り直させない。

## アンチパターン

| アンチパターン | なぜ悪いか |
| --- | --- |
| 保存のリクエストの中で読み直した版で楽観的ロックをかける | 画面を開いていた間の他人の更新を検出できない |
| `If-Match` を任意にする | 付け忘れたクライアントが黙って上書きする |
| `If-Match: *` を受け付ける | 版を確かめない上書きになる |
| 圧縮を有効にしたまま Django の `condition` で `If-Match` を判定する | 弱い ETag が一致せず、更新が常に 412 になる |
| 412 を受けて自動でリトライする | ユーザーが見ていない内容で上書きする |
| 明細ごとに版を持たせる | 集約の規則が同時編集で破れる |
| リクエストをまたいで DB のロックやトランザクションを持ち越す | 接続を握り続け、ブラウザを閉じると外れない |
| 期限のない編集ロック | 画面を閉じた人のロックが残り続ける |
| 編集ロックだけで、保存時に版を確かめない | 期限切れや強制解除のあとの保存が上書きする |
| 仮押さえをロック表で表す | 業務の事実が一覧にも集計にも出ず、失効を業務として扱えない |
| 412 で入力を捨てて再読み込みさせる | ユーザーが入力をやり直すことになる |

## ルール(チェックリスト)

- [ ] 更新対象ごとに、後勝ち・楽観的・悲観的・業務の状態のどれにするかを決めた(第 2 節)
- [ ] 後勝ちにしたものは、その理由を残した
- [ ] 読み取りが版を返し(`ETag` か hidden)、更新が版を送り返す
- [ ] 送り返された版が条件付き UPDATE まで届いている(サーバーで読み直した版を使っていない)
- [ ] 古い版は 412、版なしと `If-Match: *` は 428、フォームは 409 で、本文が Problem Details
- [ ] `If-Match` を自前で読み、`W/` を外して版の番号で比べている
- [ ] 版は集約ルートに 1 つ。子のリソースの `ETag` も親の版
- [ ] 更新のコマンド DTO の `expected_version` に既定値がない
- [ ] 更新系のエンドポイントが `If-Match` なしで 428 になることを、1 本のテストで網羅している
- [ ] 編集ロックには期限・延長・保存時の確認・強制解除があり、版の確認と併用している
- [ ] 仮押さえ・引当・担当は、集約の状態として持っている
- [ ] 競合したとき、入力を残したまま最新の内容と差分を見せる
