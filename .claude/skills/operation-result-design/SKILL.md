# 処理結果とステータスの設計 (Operation Result)

**「成功／失敗」は 1 つの軸ではない。** 混ぜると、業務上まったく正常な「却下」を
呼び出し側がリトライしたり、障害を業務結果として握り潰したりする。

エンティティが持つ状態と遷移は
[ddd-state-transition](../ddd-state-transition/SKILL.md)、
usecase での例外の分類は
[ddd-application-layer](../ddd-application-layer/SKILL.md)、
プロセス全体の失敗と補償は
[ddd-long-running-process](../ddd-long-running-process/SKILL.md)。

---

## 1. 2 つの軸を分ける

| 軸 | 問い | 呼び出し側の関心 |
| --- | --- | --- |
| **受理**(責任を引き取れたか) | 処理する責任を**果たせたか** | **リトライすべきか。作り直すべきか** |
| **業務結果** | 処理した結果**どうなったか** | 業務としてどう扱うか |

```text
「申込を受け付け、審査の結果 却下した」
  → 受理:     成功(責任は果たした)
  → 業務結果: 却下

「DB に接続できず、申込を記録できなかった」
  → 受理:     失敗(責任を果たせていない)
  → 業務結果: なし
```

**却下は失敗ではない。** 処理は正しく行われ、結果が否定的だっただけ。
これを「失敗」にすると、呼び出し側はリトライする — 何度やっても却下される。

### 判定

**「もう一度同じことをして、結果が変わりうるか」**

- 変わりうる(接続断、タイムアウト、競合) → **受理の失敗**。リトライ可。
- 変わらない(却下、残高不足、期限切れ、権限なし) → **受理は成功、業務結果が否定的**。
  リトライしても無駄。

## 2. 業務上妥当な否定的結果を例外にしない

**例外は「起きてはいけないこと」に使う。** 業務上ありふれた結果に使うと、
正常系が例外制御になる。

```python
# NG: 却下は業務として当然ありうるのに例外
def review(self, application: Application) -> Application:
    if not self._meets_criteria(application):
        raise ApplicationRejectedError()      # ← 正常な業務結果

# OK: 結果として返す
def review(self, application: Application) -> Application:
    if not self._meets_criteria(application):
        return application.reject(reason=RejectionReason.INSUFFICIENT_CREDIT)
    return application.approve()
```

| 種類 | 表現 | 例 |
| --- | --- | --- |
| **業務として起こりうる結果** | **戻り値** | 却下、残高不足、在庫切れ、対象なし |
| 不変条件の違反(呼び出し側のバグ) | 例外 | 出荷済みを再出荷しようとした |
| 技術的な失敗 | 例外 | DB 接続断、外部 API タイムアウト |

**見分け方**: 業務の人が「それはよくあることだ」と言うなら、戻り値。
「それは起きてはいけない」と言うなら、例外。

---

> 例外にすると決めた場合の設計(型階層・エラーコード・メッセージ・ログ)は
> [exception-design](../exception-design/SKILL.md)。

## 3. 例外か、結果型か

**戻り値で返すと決めたあと、その形をどうするか。**

```python
# 方式 A: ドメインオブジェクト自身が結果を表す(既定)
approved_or_rejected = application.review(...)   # status を見れば分かる

# 方式 B: 結果型(タグ付きユニオン)で分岐を強制する
@dataclass(frozen=True, kw_only=True)
class Approved:
    application: Application

@dataclass(frozen=True, kw_only=True)
class Rejected:
    application: Application
    reason: RejectionReason

ReviewResult = Approved | Rejected
```

| | 方式 A(状態を見る) | 方式 B(結果型) |
| --- | --- | --- |
| 素直さ | 高い | 中 |
| 分岐漏れ | 気付けない | **`match` の網羅性で気付ける** |
| 結果ごとに**付随データが違う** | 表現しにくい | **向いている** |

- **既定は方式 A。** 状態遷移として表せるなら、それで足りる
  ([ddd-state-transition](../ddd-state-transition/SKILL.md))。
- **方式 B は、結果ごとに持つデータが違うときだけ**(却下理由、部分成功の件数)。
- **`Result[T, E]` のような汎用型を自作しない。** Python では型チェッカとの
  相性が悪く、`match` も冗長になる。**業務の言葉で名付けた型**を並べる方がよい。
- `None` を「該当なし」と「エラー」の両方に使わない。意味が曖昧になる。

## 4. ステータスは軸ごとに別フィールドで持つ

**1 つの `Enum` に異なる軸を詰め込まない。** 組み合わせが掛け算で増える。

```python
# NG: 受理・審査・配送が 1 つに混ざり、状態数が爆発する
class OrderStatus(Enum):
    RECEIVED_PENDING_REVIEW = ...
    RECEIVED_APPROVED_NOT_SHIPPED = ...
    RECEIVED_APPROVED_SHIPPED = ...
    RECEIVED_REJECTED = ...
    FAILED_TO_RECEIVE = ...

# OK: 軸ごとに分ける
@dataclass(frozen=True, kw_only=True, eq=False)
class Order(Entity):
    review: ReviewStatus       # 業務判断の軸
    fulfillment: FulfillmentStatus   # 履行の軸
```

- **軸の見つけ方**: 「一方が変わっても、もう一方は変わらないか」。
  変わらないなら独立した軸。
- **軸の間に依存があるなら、それは不変条件**として集約が守る
  (「却下された注文は出荷されない」)。フィールドを分けても、
  整合はルートが保証する。
- 詳細は
  [ddd-state-transition](../ddd-state-transition/SKILL.md)。

## 5. リトライ可否を呼び出し側に伝える

**呼び出し側が判断できる情報を返す。** 「失敗しました」だけでは、
リトライすべきか作り直すべきか分からない。

| 分類 | 意味 | 呼び出し側の行動 |
| --- | --- | --- |
| **一時的失敗** (retryable) | 再試行で成功しうる | バックオフして再試行 |
| **恒久的失敗** (permanent) | 同じ入力では常に失敗 | 入力を直す。再試行しない |
| **不明** | 結果が確定していない(タイムアウト) | **冪等キーを付けて再試行** |

**3 つ目が最も危険。** 「タイムアウトしたが、実は処理は成功していた」が起こる。
外部呼び出しには冪等キーを渡す
([ddd-long-running-process](../ddd-long-running-process/SKILL.md))。

## 6. HTTP への対応

**受理の軸が HTTP ステータス、業務結果はボディ。**

```text
受理成功 + 業務結果「承認」  → 200/201 + {"review": "approved"}
受理成功 + 業務結果「却下」  → 200/201 + {"review": "rejected", "reason": "..."}
                                ↑ 却下は 4xx ではない。処理は正しく行われた
受理失敗(入力が不正)         → 422
受理失敗(競合)               → 409
受理失敗(権限なし)           → 403
受理失敗(障害)               → 5xx
```

- **業務上の否定的結果を 4xx にしない。** 4xx は「リクエストを直せ」の意味。
  却下はリクエストを直しても却下される。
- **「作成したが審査は保留」は 201。** リソースは作られている。
- **例外**: 業務ルール上そもそも受け付けられない要求(残高不足の送金など)を
  422 で返すのは妥当。**「受け付けたが結果が否定的」と「そもそも受け付けない」を
  区別する。**
- 変換は 1 か所(exception handler)に集約する
  ([ddd-application-layer](../ddd-application-layer/SKILL.md))。

## 7. 部分成功

**一括処理は「全部成功」か「全部失敗」とは限らない。**

```python
@dataclass(frozen=True, kw_only=True)
class BulkImportResult:
    succeeded: tuple[RowId, ...]
    failed: tuple[tuple[RowId, FailureReason], ...]
```

- **件数だけを返さない。** どれが失敗したかを返す。再実行の対象を決められない。
- **全体を成功/失敗の 1 値に丸めない。** 丸めるなら、その定義を決める
  (「1 件でも失敗したら失敗」なのか「全滅なら失敗」なのか)。
- HTTP なら 207 か、200 + ボディで内訳を返す。

## アンチパターン

| アンチパターン | なぜ悪いか |
| --- | --- |
| 却下・不許可・在庫切れを例外で表す | 正常系が例外制御になる。呼び出し側がリトライする |
| 業務上の否定的結果を 4xx で返す | リクエストを直しても結果は変わらない |
| 受理と業務結果を 1 つの `Enum` に混ぜる | 状態が掛け算で増え、あり得ない組み合わせが作れる |
| 「失敗しました」だけを返す | リトライすべきか呼び出し側が判断できない |
| タイムアウトを恒久的失敗として扱う | 実は成功していた場合に二重処理になる |
| `None` を「該当なし」と「エラー」の両方に使う | 意味が曖昧。呼び出し側で区別できない |
| 汎用 `Result[T, E]` を自作する | 型チェッカと相性が悪く、業務の意図も消える |
| 一括処理の結果を件数だけ返す | どれを再実行すべきか分からない |
| 例外メッセージの文字列で分岐する | 文言変更で壊れる。型か列挙で分岐する |
| 技術的失敗を業務結果に丸める | 障害が業務データとして記録され、気付けない |

## ルール(チェックリスト)

- [ ] **受理の成否**と**業務結果**を別の軸として分けた
- [ ] 「もう一度やって結果が変わるか」で両者を判定した
- [ ] 業務上ありふれた否定的結果(却下・在庫切れ)を**例外にしていない**
- [ ] 例外は「不変条件の違反」か「技術的失敗」にだけ使っている
- [ ] 結果型を使うのは、**結果ごとに付随データが違う**ときだけ(既定は状態で表す)
- [ ] 汎用 `Result[T, E]` を自作していない(業務の言葉で名付けた型を使う)
- [ ] ステータスを**軸ごとに別フィールド**で持っている
- [ ] 軸をまたぐ整合を集約が不変条件として守っている
- [ ] 失敗に**一時的 / 恒久的 / 不明**の区別があり、呼び出し側が行動を決められる
- [ ] タイムアウト(結果不明)に**冪等キー**で対応している
- [ ] HTTP は**受理がステータス、業務結果がボディ**。却下を 4xx にしていない
- [ ] 部分成功で**どれが失敗したか**を返している(件数だけにしていない)
