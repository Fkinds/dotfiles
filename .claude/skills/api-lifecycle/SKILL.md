# API のバージョニングと廃止 (API Lifecycle)

**公開した API は、増やすのは簡単で、変えるのと消すのが難しい。**
バージョニングは変更を通すための仕組みであり、廃止まで込みで設計する。

エラー形式そのものは
[http-error-response](../http-error-response/SKILL.md)、
ページネーションや冪等キーの取り決めは
[api-reliability](../api-reliability/SKILL.md)、
公開済みイベントのバージョニングは
[ddd-domain-events](../ddd-domain-events/SKILL.md)。

---

## 1. まず「破壊的変更か」を判定する

**バージョンを上げる判断は、この判定でしか始まらない。**

| 変更 | 破壊的か |
| --- | --- |
| レスポンスに**フィールドを足す** | ならない(クライアントが未知フィールドを無視する前提) |
| 任意のリクエストパラメータを足す | ならない |
| エンドポイントを足す | ならない |
| フィールドを**消す・改名する** | **なる** |
| フィールドの**型・単位・書式**を変える | **なる** |
| 必須パラメータを足す | **なる** |
| 既定値・並び順・上限値を変える | **なる**(気付かれにくい分たちが悪い) |
| ステータスコードやエラー形式を変える | **なる** |
| 列挙値を**足す** | 場合による。クライアントが未知の値で落ちるなら破壊的 |

- **「未知フィールドを無視せよ」「未知の列挙値で落ちるな」はドキュメントに明記する。**
  書いていなければ、追加も破壊的変更として扱うしかなくなる。
- 判定に迷うものは破壊的として扱う。取り消せない。

---

## 2. バージョニング方式を選ぶ

**標準仕様はない。** デファクトから選ぶ。

| 方式 | 例 | 向く相手 |
| --- | --- | --- |
| **パスに `v1`** | `/v1/users`(Google, Microsoft Graph) | **社内 / 自社クライアント**(既定) |
| **日付をヘッダで** | `X-GitHub-Api-Version: 2022-11-28`、Stripe | 不特定多数の公開 API |
| 日付をパスで | Shopify `2026-04`(四半期ごと) | 同上 |
| 日付をクエリで | Azure `?api-version=2023-01-01` | 同上 |

- **既定はパスの `v1`。** URL を見れば分かり、ルーティングもキャッシュも素直。
  Google AIP-185 も `v1` を必須にしている。
- **日付ベースは「クライアントを止められない」ときに検討する。** 利用者ごとに
  固定した日付を保持し、こちらは変換層を持ち続ける。**運用コストが本体。**
  規模がないなら選ばない。
- **`v1.1` を作らない。** メジャーだけにする。非破壊の変更にバージョンは要らない。
- **`v2` を作ったら `v1` の終わり方を同時に決める。** 決めないと永久に残る。
- ヘッダやクエリで選ばせる場合、**未指定時の既定を決めて明記する**
  (最新に追従させるか、最古に固定するか)。追従は静かに壊れるので原則は固定。

## 3. 廃止は機械可読に告知する

ブログや変更履歴だけで伝えない。**レスポンス自身に載せる。**

```http
HTTP/1.1 200 OK
Deprecation: @1735689600
Sunset: Sun, 01 Aug 2027 00:00:00 GMT
Link: <https://example.com/docs/migrate-v2>; rel="deprecation"; type="text/html"
```

| ヘッダ | 意味 | 根拠 |
| --- | --- | --- |
| `Deprecation` | **いつ非推奨になった/なるか**。まだ動く | RFC 9745 (2025) |
| `Sunset` | **いつ止まるか** | RFC 8594 (2019) |
| `Link` | 移行先ドキュメントの案内 | RFC 8288 |

- **書式が違う。** `Deprecation` は Structured Fields の日付(`@` + Unix 秒)、
  `Sunset` は HTTP-date。取り違えるとパースされない。
- **`Deprecation` を付けた時点で `Sunset` も決める。** 期限のない非推奨は
  誰も移行しない。
- **ログを取る。** `Sunset` までに誰が呼び続けているか分からないと止められない。
  バージョン別・クライアント別の呼び出し数を計測する。
- 段階: 告知 → 移行期間(実測が減るまで) → **短時間の計画停止で反応を見る** → 停止。
- 停止後は 404 ではなく **410 Gone** を返す。消えたことが伝わる。

## 4. OpenAPI を単一の情報源にする

OpenAPI 3.2.0(2025-09)。デファクト標準で、GitHub や Stripe は公式記述を配布している。

- **手書きのドキュメントと二重管理しない。** どちらが正かが必ずずれる。
- **実装から生成する**(FastAPI は設計の中核、ASP.NET Core は .NET 9 のテンプレート標準、
  Java は springdoc-openapi)。生成が無理なら**定義を先に書いて実装を検証する**。
- 定義をリポジトリに置き、**差分を CI で見る。** 破壊的変更を機械的に検出できる。
- `deprecated: true` を定義側にも立て、ヘッダと食い違わせない。
- レスポンス形式は **JSON 固定**でよい。`Accept` で XML/JSON を切り替える設計は
  廃れている。切り替えの分だけテストが増える。

---

## 5. 標準がない領域の調べ方

**この分野は「RFC がある/ない」が混在している。** 根拠の強さを確かめてから決める。

1. **RFC Editor** で RFC の有無を見る。あるならそれに従う。
2. **IETF Datatracker** で策定中のドラフトを見る。
   ドラフトは**期限切れ(Expired)になっていないか**まで確認する。
3. **デファクトの現物**を見る。Google AIP / Zalando RESTful API Guidelines /
   Google JSON Style Guide / GitHub・Stripe の公開 API。
4. Web API 周辺の標準化は IETF の **httpapi ワーキンググループ**が定点観測先。

- **ドラフト段階の仕様を先取りで採用しない。** 仕様が変わると破壊的変更になる。
  デファクトで出しておき、RFC になってから移す。
- **`X-` 接頭辞を新しく作らない**(RFC 6648)。標準化されたときに改名が要る。
- このスキルに書いてある RFC 番号やデファクトの実例は**スナップショット**。
  重要な判断の前には上の手順で現況を確かめる。

## アンチパターン

| アンチパターン | なぜ悪いか |
| --- | --- |
| フィールドの意味や単位を黙って変える | 型が同じなので気付かれず、静かに壊れる |
| `v1.1` `v1.2` とマイナーを切る | 非破壊の変更にバージョンは要らない。分岐だけ増える |
| `v2` を出すが `v1` の終わりを決めない | `v1` が永久に残り、両方を保守し続ける |
| 廃止をブログと変更履歴だけで告知する | クライアントの実装者に届かない |
| `Deprecation` だけ付けて `Sunset` を決めない | 期限がないので誰も移行しない |
| 呼び出し数を計測せずに停止日を迎える | 止めてよいか判断できず、結局延期する |
| 停止したエンドポイントを 404 で返す | 消えたのか間違えたのか区別できない。410 を使う |
| OpenAPI 定義と手書きドキュメントを二重管理する | 必ずずれる |
| 未指定時のバージョンを「常に最新」にする | クライアントが何もしていないのに壊れる |
| 策定中のドラフトを先取りで採用する | 仕様変更がそのまま破壊的変更になる |
| 新しく `X-` 接頭辞のヘッダを作る | RFC 6648 で非推奨。標準化時に改名が要る |

## ルール(チェックリスト)

- [ ] その変更が**破壊的かどうか**を表で判定した
- [ ] 「未知フィールド・未知の列挙値を無視せよ」をドキュメントに書いている
- [ ] バージョニング方式を相手(社内か不特定多数か)で選んだ
- [ ] メジャーだけを切っている(`v1.1` を作っていない)
- [ ] 未指定時の既定バージョンを決めて明記している
- [ ] 新バージョンを出すとき、旧バージョンの終わり方を同時に決めた
- [ ] 廃止を `Deprecation` / `Sunset` ヘッダで機械可読に告知している
- [ ] 2 つのヘッダの書式(sf-date と HTTP-date)を取り違えていない
- [ ] `Link` で移行先ドキュメントを案内している
- [ ] バージョン別・クライアント別の呼び出し数を計測している
- [ ] 停止後は 410 を返す
- [ ] OpenAPI 定義が単一の情報源で、CI で差分を見ている
- [ ] 標準の有無を RFC Editor / Datatracker で確かめ、ドラフトの先取りを避けた
