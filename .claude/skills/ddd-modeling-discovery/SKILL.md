# DDD: モデルの発見 (Modeling & Discovery)

**モデルは決めるものではなく、業務から見つけるもの。** 他の DDD スキルはすべて
「モデルが決まった後」の指針だが、その前段がここ。ここを飛ばすと、テーブル設計を
ドメインモデルと呼び替えただけのものができる。

集約の境界の引き方は
[ddd-aggregate-repository-boundary](../ddd-aggregate-repository-boundary/SKILL.md)、
見つけたものの実装は
[ddd-domain-object-completeness](../ddd-domain-object-completeness/SKILL.md)、
コンテキストの分け方は
[ddd-bounded-context](../ddd-bounded-context/SKILL.md)、
既存コードから始める場合は
[ddd-legacy-refactoring](../ddd-legacy-refactoring/SKILL.md)。
見つけたライフサイクルの実装は
[ddd-state-transition](../ddd-state-transition/SKILL.md)、
複数ステップの業務プロセスは
[ddd-long-running-process](../ddd-long-running-process/SKILL.md)。

## 1. 名詞から始めない

要件書の名詞に「エンティティ」の札を貼る進め方は、**業務の動きを落とす**。
残るのはデータの器だけで、ルールがどこにも入らない(ドメインモデル貧血症の起点)。

**出来事(何が起きるか)から始める。** 出来事には必ず、いつ・誰が・何を満たせば
起きるのかが伴う。そこにルールが宿っている。

```text
NG: 「注文」「顧客」「商品」がある → Order / Customer / Product クラスを作る
    → 「注文が取り消せる条件」がどこにも入らない

OK: 「注文された」「支払われた」「出荷された」「取り消された」が起きる
    → 「出荷済みなら取り消せない」が見つかる → Order.cancel() の中身が決まる
```

---

## 2. イベントストーミング

業務の人と一緒に、**出来事を時系列に並べる**。付箋でも Miro でもテキストでもよい。
道具ではなく順序が重要。

| 順 | やること | 出るもの |
| --- | --- | --- |
| 1 | **出来事**を過去形で洗い出し、時系列に並べる | ドメインイベント候補 |
| 2 | 各出来事の**引き金**(コマンド・時間・外部)を書く | ユースケース候補 |
| 3 | 出来事が起きる**条件**を書く | 不変条件・業務ルール |
| 4 | 条件の判定に**必要な情報**をまとめる | 集約候補 |
| 5 | 用語が**別の意味**で使われる箇所に線を引く | コンテキスト境界 |

- **過去形で書く**(「注文した」ではなく「注文された」)。命令と事実が混ざらない。
- **例外・異常系こそ聞く。** 「取り消しは?」「二重申込は?」「遡って直すことは?」
  正常系だけのモデルは本番で破綻する。
- **矛盾や「場合による」を歓迎する。** そこにコンテキスト境界か、
  未発見の概念が隠れている。

## 3. 業務の人への問いの立て方

「どんなデータが必要ですか」と聞くと、画面とテーブルの話が返ってくる。
**ルールを引き出す問い**を使う。

| 目的 | 問い |
| --- | --- |
| 不変条件を見つける | 「それが**起きない**のはどういうときですか」 |
| 同上 | 「この状態はあり得ますか」(あり得ないなら不変条件) |
| ライフサイクルを見つける | 「これは作られてから最後どうなりますか」 |
| 同一性を見分ける | 「この2つは**同じもの**ですか、同じ**値**ですか」 |
| 境界を見つける | 「その言葉、別の部署では同じ意味で使いますか」 |
| 整合性の強さを測る | 「ここがズレていたら**すぐ困りますか**、あとで直せますか」 |
| 例外を炙り出す | 「例外的に手で直すことはありますか」 |

最後の問いは特に効く。**手作業の回避策(workaround)は、モデルが業務に追いついていない
場所を正確に指している。**

> 「すぐ困るか」への答えが**強整合か結果整合か**を決め、そのまま集約の境界と
> ドメインイベントの使い分けになる
> ([ddd-domain-events](../ddd-domain-events/SKILL.md))。

## 4. 出来事から集約と不変条件を導く

イベントストーミングの結果を、**機械的に**設計へ落とす。

```text
出来事: 「注文が取り消された」
  引き金: 顧客が取消を要求した
  条件:   出荷されていない / 支払済みなら返金が必要
  必要な情報: 注文の状態、出荷の有無

→ 不変条件: 「出荷済みの注文は取り消せない」
→ 検査に必要 = Order の状態          → Order 集約の内側
→ 返金は別の関心で、即時でなくてよい  → イベント(OrderCancelled)で連携
```

判定の順序:

1. その条件を検査するのに**必ず読む必要がある**ものを列挙する。
2. それが**1つの集約**。
3. 読むだけで変更しないものは**別集約**(id 参照か、値のコピー)。
4. 「同時に変わらないと不正」でないものは**イベント**で繋ぐ。

**ここで初めてテーブルの話をしてよい。** 逆順にすると、テーブルの都合が
不変条件を歪める。

## 5. 概念が足りないサイン

モデリング中、次が出たら**まだ見つかっていない概念がある**。

| サイン | 隠れているもの |
| --- | --- |
| 同じ言葉に毎回修飾語が付く(「仮の契約」「本契約」) | 別々の概念。分ける |
| 真偽値フラグが増える(`is_active`, `is_temporary`, `is_locked`) | 状態を表す型(`Enum` / 状態オブジェクト) |
| 「〜の場合は例外的に」が多い | 別のコンテキスト、または別の集約 |
| 引数が5個以上のメソッド | 引数の一部が1つの値オブジェクト |
| 業務の人が使う言葉がコードに無い | モデルの欠落。名前を付けて実体にする |
| コードにあるが会話に出ない言葉 | 技術的都合の混入。ドメインから追い出す |
| 手作業の回避策がある | モデルが業務に追いついていない |

## 6. モデルは反復する

**最初のモデルは間違っている。** 業務の理解が深まるたびに作り直す。DDD の核心は
パターン集ではなく、この**継続的な学習(knowledge crunching)**のほう。

- **小さく作って早く当てる。** モデルを紙の上で完成させようとしない。
  動くコードに載せると、破綻が早く見える。
- **モデルが急に簡単になる瞬間(ブレイクスルー)を狙う。** 条件分岐が消え、
  名前が業務の言葉に一致する。そこまでは「まだ途中」と考える。
- **作り直しを恐れない。** 深いモデルの変更はコストが高いが、**間違ったモデルの上に
  積み上げるほうが高い**。特にコアドメインでは早めに払う
  ([ddd-bounded-context](../ddd-bounded-context/SKILL.md) のサブドメイン判断)。
- **リファクタリングの引き金は「業務の理解が変わったとき」。** コードの見た目ではない。

## 7. 成果物をどう残すか

モデリングの結論は、**コードと用語集**に残す。図は補助。

| 成果物 | 置き場所 | 寿命 |
| --- | --- | --- |
| ユビキタス言語の用語集 | `docs/glossary.md` | 長い。更新し続ける |
| ドメインイベント一覧(出来事の時系列) | `docs/domain-events.md` | 中。設計が固まるまで |
| 集約と不変条件の対応表 | コードのコメント or `docs/` | コードへ移していく |
| ホワイトボード写真・付箋 | 捨ててよい | 短い |

- **最終的な仕様はコード。** ドキュメントとコードが食い違ったら、コードを直すか
  ドキュメントを捨てる。二重管理はどちらも腐らせる。
- 用語集の書き方は
  [ddd-bounded-context](../ddd-bounded-context/SKILL.md)。

## アンチパターン

| アンチパターン | なぜ悪いか |
| --- | --- |
| 要件の名詞をそのままクラスにする | 業務の動きとルールが落ちる。貧血症の起点 |
| ER 図・テーブル設計から始める | 永続化の都合が不変条件を歪める |
| 正常系だけモデリングする | 例外・取消・遡及で破綻する。そこにルールがある |
| 「どんなデータが必要か」と聞く | 画面とテーブルの話しか返ってこない |
| 矛盾を早々に「統一」する | コンテキスト境界を潰してしまう |
| 紙の上でモデルを完成させようとする | 動かすまで破綻が見えない |
| 最初のモデルに固執する | 理解が深まっても直せなくなる |
| 図をドキュメントとして永続管理する | コードと二重管理になり、両方腐る |
| モデリングを設計者だけでやる | 業務の人の中にしかない知識が入らない |

## ルール(チェックリスト)

- [ ] **出来事(過去形)から**始めた。要件の名詞からクラスを作っていない
- [ ] 各出来事の**引き金**と**起きる条件**を書き出した
- [ ] 条件から**不変条件**を言語化した(「〜のとき〜できない」の形)
- [ ] 不変条件の検査に**必ず要るもの**から集約候補を導いた(テーブルからではない)
- [ ] 例外・取消・遡及・二重実行を業務の人に確認した
- [ ] 「**ズレたらすぐ困るか**」を聞き、強整合か結果整合かを決めた
- [ ] 手作業の回避策の有無を確認した(モデルの欠落を指している)
- [ ] 概念不足のサイン(フラグの増殖、修飾語、引数過多)を点検した
- [ ] 用語集を作り、コードの名前と一致させた
- [ ] モデルは**作り直す前提**で扱っている。理解が変わったら直す
