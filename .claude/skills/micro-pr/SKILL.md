# Micro PR — 差分だけでレビューが完結する PR に分ける

**基準は 1 つ。その PR の差分にあるファイルだけで、レビューが完結すること。**
レイヤーとクラスで切るのはそれを満たすための切り方で、300〜500 行は量の制約。

このスキルが持つのは**分け方**(計画、分割、行数の確認)だけ。

- PR を出す(draft、日本語のタイトル、ready にする順)→ [creating-stacked-prs](../creating-stacked-prs/SKILL.md)。
  `gh stack` のコマンド → [gh-stack](../gh-stack/SKILL.md)。
- リポジトリにコミットや PR の自前のスキル・規約(commitlint など)があれば、メッセージ・
  ブランチ名・PR の作り方はそちらに従う。ここが決めるのは分け方と順序だけ。

---

## 1. 基準 — 差分だけでレビューが完結する

レビューする人が差分の外で見てよいのは、呼び出す先の**公開シグネチャと型**だけ。

| 状態 | 判定 |
| --- | --- |
| 呼び出す先の名前と型を見れば、正しく使っているか判断できる | 完結している |
| 呼び出す先の実装を読まないと、正しいか判断できない | 違反。分ける前に、呼び出す先の名前や型を直す |
| 振る舞いを確かめる材料が差分にない(テストが別の PR) | 違反。テストは実装と同じ PR |
| 呼び出し側がまだなく、何のためのコードか差分から読めない | PR 本文に、スタックのどの PR から・どう使われるかを書けば足りる |
| 名前の変更・移動と、振る舞いの変更が混ざっている | 違反。振る舞いが変わった行を差分から拾えない。別の PR にする |

リファクタリングと振る舞いの変更を分ける理由と手順は
[ddd-legacy-refactoring](../ddd-legacy-refactoring/SKILL.md)。

---

## 2. 量 — 1 PR 300〜500 行

**上限 500 に例外はない。** 下限 300 の扱いは第 5 節。

| 数える | 数えない(PR 本文に一覧を書く) |
| --- | --- |
| 追加と削除の合計 | lock ファイル、スナップショット |
| テストのコード | `RunPython` / `RunSQL` を含まない migration(`makemigrations` の生成物) |
| ドキュメント(ADR、md) | テスト用ディレクトリの中のデータファイル(JSON、CSV など) |
| 手書きの migration | 生成された型定義など、リポジトリ固有の生成物 |
| データを生成するスクリプト(データと同じ PR に入れる) | バイナリ |

ファイルの移動は git の rename 検出(`-M`)をかけて数える。中身を変えない移動は 0 行に近い。

**目で数えず、スクリプトで数える。** 生成物の扱いがぶれない。

```bash
# コミット済みのブランチを数える(PR の差分と同じ、分岐点からの差分)
python3 ${CLAUDE_SKILL_DIR}/scripts/count_pr_lines.py <1 つ下のブランチ> <このブランチ>

# コミット前の作業ツリーを数える(未追跡のファイルを含む)
python3 ${CLAUDE_SKILL_DIR}/scripts/count_pr_lines.py <1 つ下のブランチ>
```

- 一番下の PR なら、`<1 つ下のブランチ>` は trunk(`main` など)。
- `-v` でファイルごとの行数を出す。`--exclude 'GLOB'` でリポジトリ固有の生成物を足す。
- 500 を超えると終了コード 1。300 未満は警告だけ出す。

---

## 3. 切り方 — レイヤーごと、閉じた単位ごと

**1 PR = 1 つのレイヤーの中で、クラスかモジュールに閉じた変更。**

- 単位の例: 値オブジェクト 1 つ、集約 1 つ、usecase 1 つ、リポジトリの実装 1 つ、
  FSD の slice 1 つ。
- **テストは実装と同じ PR に入れる。** gh-stack の「テストやドキュメントに移るときは
  新しいブランチ」という目安は採らない。
- **リファクタリング(名前の変更・移動・抽出)と振る舞いの変更は別の PR。** 同じクラスの
  中で閉じていても分ける。
- **レイヤーに属さないファイル**(設定、依存の定義、CI、ルートの URL 定義、import の
  検査の契約)は、それを最初に必要とする PR に入れる。
- 1 つのスタックは 1 つの機能。無関係の修正は別のスタックにする。

---

## 4. 順序 — 内側の層から積む

1. スタック全体は、**変更がある一番内側の層**から始める。serializer に項目を足すだけなら、
   その層から始まる。
2. 同じ層の中は、**import される側から**。
3. ADR があれば、スタックの一番下に単独で置く。300 行未満でも単独にする。

**層の名前と並びはリポジトリごとに違う。** 直書きせず、リポジトリから読む。

| 読む先 | 読み方 |
| --- | --- |
| import-linter の `layers` 契約(`pyproject.toml` / `.importlinter`) | 上に書かれた層ほど外側。下から積む |
| 層の検査スクリプト([layer-enforcement.md](../ddd-application-layer/layer-enforcement.md) の `LAYERS` など) | 依存先が少ない層ほど内側 |
| どちらもない | ディレクトリの構成から推定し、計画を出すときに確かめる |

どのディレクトリにあるかは違っても、役割で見た順序はほぼ同じになる。

| 順 | 役割 | 層の中の並び |
| --- | --- | --- |
| 1 | ドメイン | 値オブジェクト → エンティティ・集約 → リポジトリの抽象・ドメインサービス |
| 2 | usecase | 入出力の DTO・ポート → usecase |
| 3 | 永続化の実装 | モデルと migration → リポジトリの実装 |
| 4 | 入口 | serializer → view / controller |
| 5 | 組み立て | composition root → ルーティング・タスクの登録 |

FSD なら `shared → entities → features → widgets → pages → app`
([fsd-layers](../fsd-layers/SKILL.md))。

---

## 5. 量を合わせる

### 300 行に届かないとき

1. 同じ層にある、**同じ機能のための**閉じた単位をまとめる(serializer と view など)。
2. それでも届かないときだけ例外にして、PR 本文に理由を書く。変更全体が小さい、
   その層の変更がそれだけ、ADR、のどれか。

**別の層の変更や、無関係の変更を足して届かせない。** 何のための PR か差分から読めなくなる。

### 500 行を超えるとき

| 状況 | 割り方 |
| --- | --- |
| 複数の単位が入っている | 単位ごとに PR を分ける |
| 1 つのクラスだけで超える | 振る舞いごとに積む。1 本目は型とコンストラクタの不変条件(テスト付き)、2 本目以降で振る舞いを 1 つずつ(テスト付き) |
| 既存のシグネチャを変え、呼び出し側が多い | 新しいものを足す → 呼び出し側をモジュールごとに移す → 古いものを消す |
| 削除が大きい | モジュールごとに消す |
| 移動が大きい | 移動だけの PR にする。移動と同時に中身を変えない |
| データファイルが大きい | 数えない(第 2 節)。生成するスクリプトは同じ PR に入れる |

---

## 6. どの PR も単独で通る

**スタックのどの PR も、そこまでを取り込んだ状態で、ビルド・lint・テストが通る。**

- 各 PR のコミットの前に、リポジトリの品質チェック(lint、型、import の検査、テスト)を流す。
  リポジトリに品質チェックのスキルがあればそれを使う。
- 定義とすべての呼び出し側を 1 本で変えない。層をまたぎ、500 も超えやすい。新しいものを
  足す → 移す → 消す、の 3 段にする(第 5 節)。
- **抽象(リポジトリのインターフェースなどのポート)にメソッドを足すときは、抽象と
  すべての実装(テストのフェイクを含む)を同じ PR に入れる。** 抽象だけを先に出すと、
  既存の実装が抽象を満たさなくなり、その PR が通らない。層をまたぐのはこの場合だけ。
- まだ呼び出し側のないコードは、テストが使い方を示し、PR 本文が使われる先を示す。

## 7. 進め方

### A. 実装の前に計画する(こちらを主にする)

1. 変更の全体を、層と閉じた単位に分けて、下の計画の表を作る。行数は見込みでよい。
2. **表をユーザーに見せ、承認を得る。**
3. 下の PR から順に、ブランチを切って実装する。1 本ごとに品質チェックとスクリプトでの
   行数の確認をしてからコミットし、次のブランチを積む。
4. 実装の途中で 500 を超えそうになったら、その場で計画を割り直してユーザーに見せる。

### B. できあがった差分をあとから分ける

[splitting.md](splitting.md) を読む。1 つのファイルの変更を複数の PR に分けるには、
途中の状態のファイルを書き起こす必要があり(`git add -p` は対話式なので使えない)、A より重い。

### 計画の表

```markdown
| # | ブランチ | 層 | 単位 | 行数 | 前提にする外のシグネチャ | 使われる先 |
| --- | --- | --- | --- | --- | --- | --- |
| 0 | reissue/00-adr | — | 再発行の ADR | 120(例外: ADR) | — | 全体 |
| 1 | reissue/01-domain-invoice | domain | Invoice.reissue() | 380 | — | #2 |
| 2 | reissue/02-usecases-reissue | usecases | ReissueInvoice と入出力 DTO | 340 | Invoice.reissue()、InvoiceRepository | #3, #4 |
| 3 | reissue/03-infrastructure-invoice | infrastructure | モデルと migration、DjangoInvoiceRepository、ファクトリ | 430 | InvoiceRepository、ReissueInvoice | #4 |
| 4 | reissue/04-interfaces-reissue | interfaces | serializer、view、URL | 310 | build_reissue_invoice()、ReissueInvoiceCommand | — |
```

### ブランチとコミット

- **1 PR = 1 コミットで作る。** `gh stack submit` は、コミットが 1 つならその件名を
  PR のタイトルにする。レビューを受けた修正は普通のコミットで足す(件名が fixup! で始まる
  コミットを CI で落とすリポジトリがある)。
- ブランチ名とコミットメッセージはリポジトリの規約に従う。規約がなければ、ブランチ名は
  `<機能名>/<番号>-<層>-<単位>`。
- `gh stack` がある: `gh stack init --base <trunk> <最初のブランチ>` → 実装してコミット →
  `gh stack add <次のブランチ>`。
- `gh stack` がない: `git switch -c <次のブランチ> <今のブランチ>` で積む。PR の base は
  1 つ下のブランチ。下がマージされたら、上を
  `git rebase --onto <trunk> <マージされた下のブランチ> <上のブランチ>` で載せ替える。
- **push と PR の作成は、ユーザーの指示があってから。** 出すときは creating-stacked-prs か、
  リポジトリの PR のスキルに従う。

### PR 本文に足すこと

- スクリプトの「数えない行」の一覧(ファイル名と行数)。
- 300 行未満なら、例外の理由。
- 前提にする外のシグネチャと、それがどの PR(または trunk)にあるか。
- まだ呼び出し側のないコードなら、使われる先の PR と使われ方。
- 計画の表は、一番下の PR にだけ載せる(creating-stacked-prs 第 2 節と同じ)。

## アンチパターン

| アンチパターン | 何が起きるか |
| --- | --- |
| テストを別の PR にして、実装だけの PR を出す | 差分の中で振る舞いを確かめられない |
| 300 に届かせるため、別の層や無関係の変更を足す | 何のための PR か差分から読めない |
| 定義と全呼び出し側を 1 本で変える | 層で閉じず、500 も超えやすい |
| 移動と中身の変更を同じ PR に入れる | 変更が大きいと rename 検出が外れ、ファイル全体が追加と削除に見える |
| 外側の層から積む | 下の PR が上の PR の定義を待ち、単独で通らない |
| 計画せずに実装し、あとで割る | 1 つのファイルの途中の状態を書き起こすことになり、重い |
| 実装を読まないと使い方が分からない API のまま分ける | 差分だけでレビューできない |
| 行数を目で数える | 生成物やデータの扱いがぶれる |

## ルール(チェックリスト)

- [ ] どの PR も、差分と、呼び出す先の公開シグネチャ・型だけでレビューできる
- [ ] どの PR も 1 つの層の中で、クラスかモジュールに閉じている
- [ ] どの PR も 500 行以下(スクリプトで確かめた)。300 行未満なら理由を本文に書いた
- [ ] テストは実装と同じ PR にある
- [ ] リファクタリングと振る舞いの変更が別の PR になっている
- [ ] 変更がある一番内側の層から積み、同じ層の中は import される側から並べた
- [ ] どの PR も、そこまでの状態でビルドとテストが通る
- [ ] まだ呼び出し側のないコードの PR に、使われる先を書いた
- [ ] 計画の表を見せて承認を得てから、ブランチとコミットを作った
- [ ] push と PR の作成は、ユーザーの指示があってから
