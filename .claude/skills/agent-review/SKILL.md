# agent-review

既存のサブエージェント定義を点検する。新規作成は
[agent-authoring](../agent-authoring/SKILL.md)。スキルの点検は
[skill-review](../skill-review/SKILL.md)。

## 手順

1. 対象を読む。指定がなければ全部。

   ```bash
   ls ~/.claude/agents/ .claude/agents/ 2>/dev/null
   ```

2. `name` の重複と `:` を含む名前を先に潰す。ここに該当するものは**そもそもロードされて
   いない**か、片方が黙って無視されている。

   ```bash
   grep -h '^name:' .claude/agents/*.md | sort | uniq -d
   ```

3. 下の検査項目を順に当てる。
4. **指摘は「どのファイルの何が」「なぜ問題で」「どう直すか」の 3 点セット**で出す。
   description の指摘には修正案の全文を添える。

## 検査項目

### A. ロードされるか

- [ ] frontmatter に `name` と `description` がある(この 2 つだけが必須)。
- [ ] `name` が kebab-case で `:` を含まない。含む定義は**ロードされず**、デバッグログに
      エラーが出るだけで気づけない。
- [ ] `name` がツリー内で一意。同一ディレクトリ配下で重複すると、ファイルシステムの
      読み取り順でどちらか一方だけがロードされる(規定の優先順位はない)。`/doctor` が報告する。
- [ ] `name` とファイル名が一致している。一致は必須ではないが、ずれていると探せない。
- [ ] YAML が壊れていない。
- [ ] 置き場所が意図と合っている。`~/.claude/agents/`(このリポジトリの `.claude/agents/`)は
      **全プロジェクトで有効**。プロジェクト固有の前提を持つ定義がここにあるなら指摘する。

### B. description(委譲精度)

- [ ] **What と When の両方**がある。何を任せるかだけで、いつ委譲するかがない、が最頻。
- [ ] **対象が名指しされている**(ファイル・ディレクトリ・領域)。委譲の可否はここで決まる。
- [ ] 三人称で書かれている。
- [ ] **観点や検査項目を列挙していない。** 「〜も検証する」「〜も確認する」が並ぶ description は
      肥大化のサイン。観点は本文へ移す。列挙が増えるほど、どのタスクで呼ぶべきかが曖昧になる。
- [ ] 特定プロジェクト専用の前提(課題名、社内固有の名前)が入っているなら、その定義が
      全プロジェクトで有効な場所に置かれていないか確認する。
- [ ] 広すぎないか。「コードをレビューする」だけでは無関係な場面で委譲される。

### C. tools と権限

- [ ] `tools` が明示されているか。省略は全ツール継承。読み取り専用のつもりの定義に
      `Write` / `Edit` が残っていないか。
- [ ] `Agent` が入っていないか。入っていると自分の下にサブエージェントを作れる。
      読み取り専用のレビュアーには不要。
- [ ] **`Write` / `Edit` を持つ定義は、書き込み先が機構的に縛られているか。** 「`tests/` 配下
      にのみ書く」のような本文の指示は、親セッションが `acceptEdits` / `auto` のとき
      許可プロンプトなしで素通りする。確実に縛るなら frontmatter の `hooks` に
      `PreToolUse` を書いてパスを検証する。
- [ ] **背景実行で消えるツールに依存していないか。** サブエージェントは既定で背景実行され、
      背景では組み込みツールが `Read` / `Grep` / `Glob` / `Bash` / `PowerShell` / `Edit` /
      `Write` / `NotebookEdit` / `WebFetch` / `WebSearch` / `TodoWrite` / `Skill` /
      `ToolSearch` / `EnterWorktree` / `ExitWorktree` / `Monitor` / `TaskStop` /
      `SendMessage` / `Artifact` に絞られる。それ以外は `tools` に書いても消える
      (MCP ツールは残る)。前景では動くので気づきにくい。
- [ ] 綴り間違いがないか。`tools` の全エントリが解決しないと**起動に失敗する**。
- [ ] `permissionMode` に `bypassPermissions` を入れていないか。入れる理由があるか。
- [ ] `disallowedTools` と `tools` の併記が意図通りか(`disallowedTools` が先に適用され、
      残りに `tools` が効く)。

### D. システムプロンプト本文

- [ ] **会話履歴なしで成立するか。** サブエージェントは主会話の履歴も、読まれたファイルも、
      起動済みスキルも見ない。「先ほどの変更」「対象のファイル」で始まる定義は、対象の
      見つけ方(`git diff` のコマンドなど)から書き直す。
- [ ] **親へ返す内容が指定されているか。** 親に届くのは最終テキストだけ。指定がないと
      調査の過程を返してきて、文脈を節約するという目的が崩れる。形式・順序・分量を書く。
- [ ] 問題がなかったときの振る舞いが書いてあるか。書いていないと指摘を捏造する。
- [ ] **CLAUDE.md の内容を書き写していないか。** CLAUDE.md は組み込みの Explore / Plan を
      除くすべてのサブエージェントに読み込まれる。重複は本文を太らせるだけ。
- [ ] 長すぎないか。目安 150 行。300 行超はたいてい責務が 3 つ混ざっている。
- [ ] 手順が番号付きで、判断が表かチェックリストになっているか。
- [ ] `memory` を設定しているなら、何を記録するかが本文に書いてあるか。

### E. 責務

- [ ] 1 定義 1 役割か。description に「かつ」が要るなら分割を提案する。
- [ ] **そもそもサブエージェントである必要があるか。** 会話の文脈が要る作業、往復が要る
      作業はスキルか主会話が向く。判断軸は
      [agent-authoring](../agent-authoring/SKILL.md) の冒頭。
- [ ] 同じ内容のスキルと重複していないか。重複はどちらが起動すべきかを曖昧にする。
- [ ] 他の定義と対象範囲が重なっていないか。

## 症状別の処方

| 症状 | 原因 | 直し方 |
| --- | --- | --- |
| 委譲されない | description に対象・トリガー語がない | 対象ファイルや領域を名指しする。積極的に使ってよいことを書く |
| 委譲されない(@-mention は動く) | frontmatter の YAML 破損 / `name` 重複 | `/doctor` と重複チェック。デバッグログを見る |
| 定義が一覧に出ない | `name` に `:` が入っている / ディレクトリ新設後に未再起動 | 名前を直す。スコープ初回の追加時のみ再起動する |
| 勝手に委譲される | description が広い、対象が抽象的 | 対象と条件を具体化する |
| 起動に失敗する | `tools` のエントリが 1 つも解決しない | エラーが挙げた名前の綴りを直す |
| 前景では動くのに背景で挙動が変わる | 背景で組み込みツールが絞られる | 検査項目 C の一覧にあるツールだけで組み立て直す |
| 返ってくる量が多すぎる | 本文に報告形式の指定がない | 「何を、どの形式で、どこまで返すか」を本文に書く |
| 何も見つからないのに指摘が返る | 問題なしのときの振る舞いが未定義 | 「問題がなければ指摘を作らない」と明記する |
| 見当違いの対象を調べる | 会話履歴を前提にした本文 | 対象の特定手順を本文に書く |

## 動作で確かめる

読むだけで終わらせない。

1. `@agent-<name>` で強制的に走らせ、出力の質と分量を見る。委譲精度とは分けて評価する。
2. description に合う自然な言い方で頼み、自動委譲されるか見る。
3. 委譲されるべきでない言い方でも試し、誤委譲しないか見る。
4. **新しいセッションで試す。** 定義を書いた会話の文脈が指示不足を隠す。
5. transcript で実際のツール呼び出しを追う。

   ```bash
   ls ~/.claude/projects/*/<session-id>/subagents/
   ```

## 報告

- 落ちた検査項目を深刻度順(ロードされない > 委譲されない > 誤委譲 > 出力品質 > 冗長)に並べる。
- description の指摘には**書き換え案の全文**を添える。
- 分割・統合の提案は、何と何に割るかまで書く。
- スキルにすべき定義は、その理由とともに指摘する。
- 問題がなければ「点検した項目」と「問題なし」を簡潔に伝える。指摘を作らない。
