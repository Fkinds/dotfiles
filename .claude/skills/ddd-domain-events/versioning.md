# 永続化・公開イベントのバージョニング

[ddd-domain-events](SKILL.md) 第 8 節の詳細。ペイロードがデプロイをまたいで永続化・配送待ちに
なる場合や、発行側と購読側を原子的に更新できない場合に使う。対象は統合イベントに限らない。
同じコンテキスト内でも、キュー、ローリングデプロイ、独立した購読プロセスがあれば互換性が要る。

同一プロセス内で同期消費し、すべての利用箇所を同時に変更でき、古いペイロードも残らない場合
だけ、通常のリファクタリングとして扱う。

## 互換性をどちら向きに保証するか

「後方互換」という言葉だけでは、誰がどの版を読むのか分からない。変更前に、少なくとも次の
二つを分けて確認する。

- 新しい購読側が、保存済みまたは配送待ちの古いペイロードを読めるか。
- 古い購読側が、先に更新された発行側の新しいペイロードを読めるか。

互換性は JSON、Avro、Protobuf などの形式、スキーマレジストリの設定、未知フィールドを
許すかどうかで変わる。次の表を、実際のシリアライザと購読側で検証する。

| 変更                         | 新しい購読側が旧版を読む | 古い購読側が新版を読む   | 方針                                               |
| ---------------------------- | ------------------------ | ------------------------ | -------------------------------------------------- |
| 任意フィールドを追加         | 既定値があれば読める     | 未知フィールドを許す場合 | 両方向を契約テストで確認する                       |
| 必須フィールドを追加         | 読めない                 | 形式による               | 任意にするか、新しいスキーマにする                 |
| フィールドを改名             | そのままでは読めない     | そのままでは読めない     | 一時的な二重フィールドか、新しいスキーマにする     |
| フィールドを削除             | 形式による               | 旧版がその値を使うと失敗 | 購読側を先に移行する                               |
| 型を変更(値の意味は同じ)     | 版別の変換があれば読める | そのままでは読めない     | 新しいスキーマにする                               |
| 単位、基準、フィールドの意味 | 読めても誤解する         | 読めても誤解する         | 名前を再利用せず、新しいフィールドとスキーマを使う |
| 出来事自体の意味を変更       | 別の事実として扱う       | 別の事実として扱う       | 新しい `event_type` にする                         |
| `event_type` を変更          | 旧名の経路には届かない   | 新名を扱えない           | 並行稼働期間を設ける                               |

`amount` を税込から税抜へ変えるような意味の変更は、構造が同じでも互換ではない。既存の `amount`
を別の意味で再利用せず、新しいスキーマで `subtotal` などの名前を追加する。出来事そのものが別の
業務上の事実になる場合は、`event_type` も分ける。

## 破壊的変更は新しい契約として出す

破壊的変更では、既存の契約をその場で書き換えず、新旧を識別できるようにする。何を変更したかと
配送基盤の制約から、`event_type` と `schema_version` の役割を分けて考える。

- 業務上の事実そのものが変わるなら、新しい `event_type` として表す。
- 同じ事実の payload 契約を破壊的に変えるなら、`schema_version` で識別する。互換変更でも
  スキーマレジストリや契約管理が版を付ける場合は、その規約に従う。公開済みフィールドの意味は
  上書きせず、新しいフィールド名を使う。
- 配送基盤が `event_type` だけで版をルーティングする場合は、`OrderPlacedV2` のような版付きの型名も
  選べる。この場合の `V2` は、事実ではなく payload 契約の版を表す。

`event_type` と `schema_version` は併存できるが、同じ互換性変更を両方で重複して表さない。
購読側がどの事実を処理するかは `event_type`、同じ事実のどの配送形式を読むかは
`schema_version`、というように役割を契約へ明記する。

```python
from dataclasses import dataclass
from decimal import Decimal


@dataclass(frozen=True, kw_only=True)
class OrderPlacedV1Payload:
    order_id: str
    total_amount: Decimal


@dataclass(frozen=True, kw_only=True)
class OrderPlacedV2Payload:
    order_id: str
    subtotal: Decimal
    tax: Decimal
    currency: str
```

この `V1` / `V2` は、同じ `OrderPlaced` という事実の payload schema を区別している。
`event_type` は変えず、`schema_version` を 2 にする例である。

ここで `Decimal` はアプリケーション内部の型である。公開ペイロードへ変換するときは、後述する
10 進数の文字列か最小通貨単位の整数を使う。

`currency` を payload に持たせるのは、後述するとおり金額の契約に通貨が要るためである。内部型に
通貨がないと、公開ペイロードへ変換する時点で値を作り出すことになる。

この例では、`total_amount` だけから `subtotal` と `tax` を正確に復元できるとは限らない。税率、
丸め、非課税明細などの情報がなければ、旧 payload を V2 へ推測変換しない。V1 に `currency` が
なければ、それも同じく補わない。

## 購読側を先に移行する

基本の移行順序は次のとおり。

1. 購読側を更新し、旧版と新版の両方を読めるようにする。
2. 発行側を更新し、新版の発行を始める。
3. 旧版の配送待ち件数、購読遅延、保存期間を監視する。
4. 旧版が届かないことを確認してから、旧ハンドラとシリアライザを削除する。

すべての購読側を新版対応にしてから発行側を切り替えられない場合に限り、旧版と新版の二重発行を
検討する。

二重発行を選ぶ理由は「新版に上げられない購読側が残っている」ことなので、その購読側へ新版が
届かない経路を先に用意する。版ごとに `event_type` を分ける、購読先ごとに版を固定する、配送基盤側
でフィルタするなど手段は基盤によるが、版のルーティングは省略できない。同じ `event_type` のまま
両版を流すと、旧版しか読めない購読側に新版が届いてデシリアライズで失敗する。旧版の wire 契約も
そのまま保つ。新版のために足したフィールドを旧版へ入れると、未知フィールドを拒否する購読側を
壊す。

そのうえで、二重発行では同じ業務上の事実から二つのメッセージが生まれるため、両版を受け取る
購読側 (移行済みで新旧どちらも読めるもの) には、個別の `event_id` に加えて共通の
`logical_event_id` を渡し、二重処理を防ぐ。`logical_event_id` は版を固定できない購読側の代わりに
はならない。

## 永続ペイロードは意味を変えない

`outbox` のペイロードは、作成時点の公開契約で配送する。未送信の旧行を新しい DTO へ強制変換
すると、デプロイ前後で同じ行の意味が変わる。版ごとのシリアライザを残し、記録した版として
送る。

`upcasting` は、イベントログや event store から古い構造を読み、アプリケーション内部で
統一した形を使う必要がある場合に限って検討する。安全に変換できるのは、値の意味を変えない
構造変更である。例えば、upcaster が版に応じて呼ぶ V1 の正規化関数は次のように書ける。

```python
def normalize_order_placed_v1(payload: dict[str, object]) -> dict[str, object]:
    return {
        "order_id": payload["order_id"],
        "total_amount": payload["total_amount"],
    }
```

- 変換関数は純粋関数にし、現在の DB やドメインロジックを参照しない。
- 扱うのは wire 上の `dict` であり、`Decimal` などアプリケーション内部の型への変換は、この後の
  デシリアライズで行う。
- 旧版で任意だったフィールドは、契約に既定値が書いてある場合だけ補う。既定値のないフィールドは
  補わない。
- 旧ペイロードにない値を推測して補わない。正本から再生成する場合は、新しいイベントとして
  発行し、再生成の理由と元イベント ID を記録する。
- 変換の連鎖が長くなったら、データ移行で読み取り対象を減らせるか検討する。

## 保存・配送形式を安定させる

公開イベントは、`envelope` と `payload` を分ける。

```json
{
  "event_id": "5f0c6a1e-...",
  "event_type": "order-placed",
  "schema_version": 2,
  "occurred_at": "2026-09-01T12:34:56Z",
  "aggregate_id": "9b2d4e7a-...",
  "correlation_id": "c3a8f210-...",
  "payload": {
    "order_id": "9b2d4e7a-...",
    "subtotal": "1000",
    "tax": "100",
    "currency": "JPY"
  }
}
```

- 金額は 10 進数の文字列か最小通貨単位の整数にし、通貨と丸め規則を契約に含める。
- 日時はタイムゾーン付き ISO 8601、UUID などの識別子は文字列で表す。
- `Enum` は Python の `name` や内部の数値を直接出さず、公開契約用の安定した文字列へ変換する
  ([ddd-state-transition](../ddd-state-transition/SKILL.md))。
- 値オブジェクトの `pickle` やクラス名依存のシリアライザを公開形式にしない。
- 未知の `event_type` や `schema_version` は隔離して通知する。契約で無視を許可した場合だけ
  `ACK` して破棄する。

## 変更前の確認

- [ ] 発行側、購読側、保存済みペイロード、配送待ち `outbox` を列挙した。
- [ ] 新旧両方向の読み取りを fixture で試した。
- [ ] 出来事自体の変更か、同じ出来事の payload 契約変更かを区別した。
- [ ] 公開済みフィールドの意味を上書きせず、新しい名前とスキーマを用意した。
- [ ] 購読側が `event_type` と `schema_version` をそれぞれ何の判定に使うか決めた。
- [ ] 購読側を先にデプロイできる順序にした。
- [ ] 二重発行する場合の版のルーティングと、両版を受け取る購読側の重複排除方法を決めた。
- [ ] 旧版を削除できる観測条件と保存期間を決めた。
