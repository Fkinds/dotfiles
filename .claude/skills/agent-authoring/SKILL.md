# agent-authoring

サブエージェント定義を 1 つ作り、委譲されることを確認するまでの手順。

既存定義の点検は [agent-review](../agent-review/SKILL.md)。スキルを作るなら
[skill-authoring](../skill-authoring/SKILL.md)。

## そもそもサブエージェントにすべきか

**サブエージェントは会話履歴を持たない。** 主会話が読んだファイルも、起動済みのスキルも、
これまでのやり取りも見えない。渡されるのは自身のシステムプロンプトと、委譲時に主 Claude が
書いた 1 通のタスクメッセージ、そして CLAUDE.md と git status だけ。

この 1 点が使い分けを決める。

| 手段 | 文脈 | 向く場面 |
| --- | --- | --- |
| 主会話 | 全部ある | 往復が要る、フェーズ間で文脈を共有する、小さな変更、速さ優先 |
| スキル | 全部ある | 手順や知識を再利用したい。主会話の文脈で動かしたい |
| **サブエージェント** | **無い** | 出力が大量で本文脈に残したくない。ツールを制限したい。自己完結して要約だけ返る |
| fork(`/subtask`) | 全部ある | 会話の続きを別文脈で走らせたい。名前付き定義は不要 |

サブエージェントにする判断は 3 つのうちどれか:

1. **文脈の隔離。** テスト実行、ログ解析、広範な検索。詳細は捨てて要約だけ戻せばよい。
2. **権限の強制。** 読むだけ、書かせない、特定の MCP サーバだけ、を定義で縛る。
3. **同じ指示の再利用。** 毎回同じ前置きを貼って同じ種類の作業を投げている。

**手順や知識を渡したいだけならスキルにする。** 判断に迷ったら、その作業に会話の文脈が
要るかを見る。要るならスキル、要らないならサブエージェント。

両方使う手もある。サブエージェント定義の `skills` フィールドはスキル本文をまるごと
起動時に注入する。「知識はスキル、隔離と権限はサブエージェント」で分けられる。

## ステップ1 — 置き場所と名前を決める

| 置き場所 | 有効範囲 | 優先度 |
| --- | --- | --- |
| managed settings の `.claude/agents/` | 組織全体 | 1(最高) |
| `--agents` フラグ(JSON) | そのセッションのみ | 2 |
| `.claude/agents/` | そのプロジェクト | 3 |
| `~/.claude/agents/` | 自分の全プロジェクト | 4 |
| プラグインの `agents/` | プラグインが有効な場所 | 5(最低) |

**このリポジトリでは** `.claude/agents/<name>.md` に置く。`~/.claude/agents` がここへの
symlink なので、置いた時点で**全プロジェクトで効く**。プロジェクト固有のものを作る気で
書くと、無関係なリポジトリで誤って委譲される。

命名:

- kebab-case。`:` は使えない(プラグインのスコープ名の区切りに予約されている)。
  含む定義はロードされず、デバッグログにエラーが出るだけで静かに死ぬ。
- **識別子は `name` フィールドだけ。** ファイル名と一致しなくても動くが、必ず揃える。
  サブディレクトリに置いても識別子は変わらない。
- **同じディレクトリツリーで `name` が重複すると、どちらか一方しかロードされない**
  (選択はファイルシステムの読み取り順で、規定がない)。`/doctor` が重複を報告する。
- 何を任せるかが名前だけで分かる名詞句(`django-backend-reviewer`)。`helper` は不可。

## ステップ2 — description を書く

`name` と `description` だけが必須。**description は自動委譲の唯一の判断材料**で、
本文(システムプロンプト)は判断に使われない。

```yaml
---
name: migration-reviewer
description: Django のマイグレーションファイルを点検する。migrations/ 配下の変更が対象。破壊的変更・巻き戻し不能な操作・本番でロックを取る操作を指摘する。マイグレーションを追加・変更したとき、PR にマイグレーションが含まれるときに使う。
tools: Read, Grep, Glob, Bash
---
```

書き方:

- **三人称で、What と When の両方。** 「何を任せるか」と「いつ委譲するか」。
- **対象を具体的に絞る。** 触るファイル・ディレクトリ・領域を名指しする。委譲の可否は
  ここで決まる。
- 待たずに使ってほしいなら「積極的に使う」に相当する語を入れる(英語なら
  `use proactively`)。
- **1 つの description に領域を詰め込まない。** 「あれもこれも検証する」と列挙するほど、
  どのタスクで呼ぶべきかが曖昧になり、委譲が外れる。観点は本文へ書く。

description は委譲の入口だけを決める。**細かい検査項目や観点は本文に書く**のが正しい
分担で、description に全部並べるのは肥大化のサイン。

## ステップ3 — tools を絞る

省略すると、サブエージェントが使える全ツールを継承する。**読むだけの定義には明示的に
`tools` を書く。**

```yaml
tools: Read, Grep, Glob, Bash          # 許可リスト
disallowedTools: Write, Edit           # 拒否リスト(継承したまま一部を落とす)
```

- 両方あると `disallowedTools` が先に適用され、残りに `tools` が効く。両方に載ったものは消える。
- MCP はサーバ単位で書ける(`mcp__github` / `mcp__github__*`、拒否側は `mcp__*` も可)。
- **`tools` の全エントリが解決しないと起動に失敗する**(綴り間違い、サブエージェントが
  使えないツール名)。エラーに未解決のエントリ名が出る。
- `Agent` を書かなければ、そのサブエージェントは自分の下にサブエージェントを作れない。
  読み取り専用のレビュアーには入れない。

### 背景実行で消えるツール(見落としやすい)

サブエージェントは**既定で背景実行**され、背景では組み込みツールが次だけに絞られる。
`tools` に書いてあっても消える。

```text
Read, Grep, Glob, Bash, PowerShell, Edit, Write, NotebookEdit, WebFetch,
WebSearch, TodoWrite, Skill, ToolSearch, EnterWorktree, ExitWorktree,
Monitor, TaskStop, SendMessage, Artifact
```

MCP ツールは背景でも残る。上記以外の組み込みツール(`AskUserQuestion` などはそもそも
全サブエージェントで使えない)を当てにした定義は、前景では動いて背景で静かに挙動が
変わる。前景実行が要るなら `background: false` ではなく、委譲時に前景を指示する
(`background: true` は常に背景にする指定であり、逆の固定はない)。

## ステップ4 — システムプロンプト本文を書く

本文がそのままシステムプロンプトになる。Claude Code の標準システムプロンプトは入らない。

**会話履歴が無い前提で、自己完結させる。** 「先ほどの変更」「さっき読んだファイル」は
通じない。対象の見つけ方から書く。

```markdown
## 手順

1. `git diff --name-only main...HEAD -- '*/migrations/*.py'` で対象を洗い出す。
2. 各ファイルを読み、下の検査項目を当てる。
3. 指摘は「どのファイルの何行が」「なぜ問題で」「どう直すか」の 3 点で書く。
```

**親に返るのは最終テキストだけ。** 何をどの形式で返すかを本文で指定する。指定が無いと、
調べた過程を延々と返してきて、文脈を節約するという目的が崩れる。

```markdown
## 報告

- 指摘を深刻度順に並べる。各指摘は 3 行以内。
- 問題がなければ「点検した項目」と「問題なし」だけを返す。指摘を作らない。
- 読んだファイルの一覧や調査の過程は返さない。
```

その他:

- 手順は番号付き、判断は表かチェックリスト。散文に埋めない。
- **CLAUDE.md は読み込まれる**(組み込みの Explore と Plan だけ例外)。プロジェクト規約を
  本文に書き写さない。
- 長さは 150 行を目安にする。超えるなら観点を絞るか、定義を分ける。300 行超の定義は
  たいてい「1 つのサブエージェントに 3 種類の仕事をさせている」。

## ステップ5 — 残りの frontmatter を決める

必要なものだけ書く。既定で困らないものは書かない。

| フィールド | 使いどころ |
| --- | --- |
| `model` | `sonnet` / `opus` / `haiku` / `fable` / モデル ID / `inherit`。既定は `inherit`。機械的な検索や集計は `haiku` に落とす |
| `effort` | `low` 〜 `max`。セッションの推論強度を上書きする |
| `skills` | スキル本文を起動時に注入する。`disable-model-invocation: true` のスキルは指定できない |
| `permissionMode` | 権限の扱い。親が `bypassPermissions` / `acceptEdits` / auto のときは親が優先され無視される |
| `memory` | `user` / `project` / `local`。会話をまたいで学習させる。有効にすると Read/Write/Edit が自動で付く |
| `isolation: worktree` | 一時 worktree で走らせる。並行して書き換えるときだけ |
| `maxTurns` | 暴走の上限 |
| `color` | タスク一覧での表示色 |
| `background: true` | 常に背景で走らせる |

`memory` を使うなら、本文にも「何を記録するか」を書く。書かないと記録されない。

## ステップ6 — 動作を確認する

1. **反映を確認する。** ファイルの追加・編集は数秒で反映され、再起動は要らない。ただし
   **そのスコープで最初の 1 個目**(`agents` ディレクトリを新規に作った場合)は再起動が要る。

   ```bash
   ls ~/.claude/agents/ .claude/agents/ 2>/dev/null
   ```

2. **@-mention で強制的に走らせ、出力品質を見る。** 委譲されるかとは別問題として先に潰す。

   ```text
   @agent-migration-reviewer 直近の変更を見て
   ```

3. **自然な言い方で自動委譲されるか見る。** 委譲されなければ description の対象語を疑う。
   逆に無関係な場面で走るなら description が広すぎる。
4. **新しいセッションで試す。** 定義を書いた会話の文脈が、本文の指示不足を隠す。
   サブエージェントは会話履歴を持たないので、この差が特に出やすい。
5. 返ってきた内容を見る。過程が長々と返るなら、本文の「報告」の指定が足りない。
6. 詳しく追うなら transcript を読む。

   ```bash
   ls ~/.claude/projects/*/<session-id>/subagents/
   ```
