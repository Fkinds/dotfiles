# セッション状態の置き場所 (Session State)

**まだ業務の事実になっていない、1 人のユーザーの作業途中の状態をどこに置くか。**
置き場所ごとに、寿命・改ざんされうるか・誰と共有されるかが違う。それで選ぶ。

出典は Martin Fowler『Patterns of Enterprise Application Architecture』の
Session State Patterns(クライアント・サーバー・データベースの 3 つの置き場所)。
各パターンの要約は[著者のカタログ](https://martinfowler.com/eaaCatalog/)にある。

関連スキル:

- フロントエンドでの URL の状態とルートパラメータ → [fsd-pages-layer](../fsd-pages-layer/SKILL.md)
- 下書きを状態として持つときの型の分け方 → [ddd-state-transition](../ddd-state-transition/SKILL.md)
- 仮押さえのように、確保に業務上の意味があるもの → [edit-conflict-control](../edit-conflict-control/SKILL.md) 第 7 節

## 1. セッション状態か、業務データか

最初に、それが**セッション状態**なのか、すでに**業務データ**なのかを分ける。

| 問い | はい → 業務データ(DB の業務テーブル) |
| --- | --- |
| 本人以外(担当者・管理者・他の利用者)が見るか | 申込の下書きを担当者が確認する |
| 業務の規則がその存在に依存するか | 仮押さえ中の席は他の人が取れない |
| 集計や分析の対象になるか | 放置されたカートの件数を追う |
| 端末をまたいで続きができる必要があるか | PC で始めてスマホで続ける |

**どれにも当たらないものだけがセッション状態。** 当たるものを Cookie や Django の
セッションに置くと、見えない・集計できない・規則を守れない。

## 2. 置き場所の比較

| 置き場所 | 寿命 | 改ざん | 共有の範囲 | 大きさ |
| --- | --- | --- | --- | --- |
| **URL**(パス・クエリ文字列) | リンクがある限り | 自由に書き換えられる | リンクを渡した相手にも | 小さい |
| **React の state** | 画面を再読み込みするまで | 自由に書き換えられる | そのタブだけ | 制限なし |
| **sessionStorage** | タブを閉じるまで | 自由に書き換えられる | そのタブだけ | 数 MB |
| **localStorage** | 消すまで | 自由に書き換えられる | 同じ端末・同じブラウザの全タブ | 数 MB |
| **Cookie** | 期限まで | 署名しなければ書き換えられる | 毎リクエストでサーバーへ送られる | 約 4 KB |
| **Django のセッション** | `SESSION_COOKIE_AGE`(既定 2 週間) | できない(サーバー側) | 同じブラウザの全タブ | 中 |
| **DB(業務テーブル・途中状態の表)** | 消すまで | できない | 決めた範囲 | 制限なし |

- **クライアントに置いたもの(上の 5 つ)は、すべて利用者が書き換えられる。** 第 4 節。
- **Django のセッションは同じブラウザの全タブで共有される。** タブごとに独立した作業を
  置くと、タブ同士で上書きし合う(第 5 節)。
- **サーバーのプロセスのメモリ(モジュールの変数・プロセス内のキャッシュ)には置かない。**
  ワーカーが複数あると、次のリクエストは別のプロセスに届く。

## 3. 状態の種類ごとの既定

| 状態 | 既定の置き場所 | 別の置き場所を選ぶ条件 |
| --- | --- | --- |
| 検索条件・並び順・ページ・選択中のタブ | **URL** | URL に出せない(個人情報を含む)→ React の state |
| 画面の中だけの一時的な状態(開閉・入力途中) | **React の state** | — |
| 長いフォームの入力途中 | **React の state** | 失うと痛い → localStorage に自動保存。端末をまたぐ → DB の下書き |
| 複数ステップの申込(ウィザード) | **クライアントが全ステップを持ち、最後に 1 回で送信** | 中断して後日再開する・端末をまたぐ → DB の下書き |
| ログインしていない人のカート | **localStorage** | サーバーで在庫や価格を確かめ続けたい → DB(匿名 ID で紐付け) |
| ログインした人のカート | **DB** | — |
| ログイン状態 | **Django のセッション + Cookie**(第 6 節) | 他社のクライアント・モバイルアプリ → トークン |

ウィザードの各ステップの検証は、**ステップごとの検証用エンドポイント**を呼んで行う。
状態はサーバーに残さない。実装例は [drafts.md](drafts.md)。

## 4. クライアントに置いた状態を信用しない

URL・React の state・Web Storage・Cookie は、利用者が自由に書き換えられる。

- **サーバーは受け取った値を毎回検証し直す。** カートの価格、選択した商品の ID、
  ウィザードの途中で決まった金額は、確定時にサーバーで計算し直す。クライアントが
  送ってきた合計額を使わない。
- **権限や役割をクライアントの値で判断しない。** 画面の表示を切り替えるのに使うのはよいが、
  操作の可否はサーバーが決める。
- **サーバーが作った値を往復させるなら署名する**(`django.core.signing`)。改ざんを検出できる。
  署名しても**中身は読める**ので、秘密は入れない。
- **秘密や個人情報を localStorage と URL に置かない。** localStorage は XSS で読まれる。
  URL はアクセスログ・ブラウザの履歴・`Referer` に残る。

## 5. Django のセッションを使うとき

| バックエンド(`SESSION_ENGINE`) | 向くとき | 注意 |
| --- | --- | --- |
| `db`(既定) | 迷ったらこれ | 期限切れの行が溜まる。`clearsessions` を定期実行する |
| `cached_db` | 読み取りが多く、速さが要る | 書き込みは DB にも行く |
| `cache` | 消えても困らない状態だけ | キャッシュの追い出しでログアウトされる。`LocMemCache` はプロセスごとに別なので使えない |
| `signed_cookies` | サーバーに何も置きたくない | 実質クライアントに置く状態。ログアウトしても盗まれた Cookie は期限まで有効 |

- **値は JSON にできるものだけ**(既定のシリアライザは `JSONSerializer`)。モデルの
  インスタンスを入れず、ID を入れて使うときに読み直す。
- **入れ子の値を書き換えたら `request.session.modified = True`。** トップレベルのキーへの
  代入しか、変更として検知されない。
- **タブごとの作業はキーを分ける。** ウィザードの状態を `session["wizard"]` に置くと、
  2 つのタブで同時に申し込んだときに混ざる。作業ごとの ID をキーにするか、
  クライアントに持たせる(第 3 節)。
- **ログイン時にセッションキーが作り直される**(`login()` が `cycle_key()` を呼ぶ)。
  ログイン前のセッションの値は引き継がれるが、キーは変わる。

## 6. ログイン状態 — Cookie のセッションか、トークンか

| 状況 | 選ぶもの |
| --- | --- |
| 自社の SPA を、API と同じサイト(同じ登録ドメイン)から配信する | **Django のセッション + Cookie**。DRF の `SessionAuthentication` |
| 他社のクライアント・モバイルアプリ・別ドメインのサービスが呼ぶ | **トークン**(アクセストークン + リフレッシュトークン) |

- **Cookie のセッションを既定にする。** `HttpOnly` で JavaScript から読めず、サーバー側で
  消せば即座に無効になる。DRF の `SessionAuthentication` はログイン済みのリクエストに
  CSRF の検証を強制するので、SPA は CSRF トークンを送る。
- **JWT をアクセストークンに使うなら、期限を短くする。** 署名だけで検証できる代わりに、
  発行後に取り消すにはサーバー側に失効リストが要る。失効リストを持つなら、
  セッションと比べた利点は薄い。
- **トークンを localStorage に置かない**(第 4 節)。ブラウザで使うなら `HttpOnly` の Cookie に入れる。
- **JWT の中の権限は発行時点の値。** 権限を外しても期限までは残る。重要な操作は
  リクエストごとに DB で確かめる。

## 7. DB に途中の状態を置くとき — 下書きの 2 つの形

| | 業務の集約の状態にする | 途中状態の表に置く |
| --- | --- | --- |
| 形 | `Application` の状態 `DRAFT` | `checkout_drafts` 表に入力を JSON で保存 |
| 向く | 下書き自体が業務の概念(担当者が見る・持ち主がいる・一覧に出る) | まだ業務の概念ではない(本人が続きをするためだけ) |
| 規則 | 下書き用の型を分け、提出時に全部の規則を通す | 入力をそのまま持ち、確定時に集約を作るときに検証する |
| 片付け | 業務の規則で決める(30 日で自動取り下げ、など) | 期限を持たせ、定期処理で消す |

- **下書きを保存するために、集約の不変条件を緩めない。** 「下書きのときは金額が空でもよい」
  を本体の型に入れると、提出済みの申込でも空を許すことになる。下書きは**別の型**にする
  ([ddd-state-transition](../ddd-state-transition/SKILL.md) 第 4 節、
  [ddd-domain-object-completeness](../ddd-domain-object-completeness/SKILL.md))。
- 途中状態の表の JSON には形のバージョンを入れる
  ([data-source-patterns](../data-source-patterns/SKILL.md) の mapping.md 第 2 節)。

実装例(下書き用の型、途中状態の表と片付け)は [drafts.md](drafts.md)。

## 8. 片付けと形の変化

すべての置き場所に**寿命**を決める。決めないと溜まり続けるか、古い形のまま読まれる。

- Django のセッション(`db`)は `clearsessions` を定期実行する。
- 途中状態の表は、期限切れの行を定期処理で消す。
- **localStorage に保存する値にも形のバージョンを入れる。** デプロイで形が変わると、
  利用者の端末に古い形が残る。読めない形は捨てる。
- URL に入れる検索条件も、パラメータ名を変えるときは古い名前をしばらく読み替える。
  共有されたリンクや、ブックマークが壊れる。

## アンチパターン

| アンチパターン | なぜ悪いか |
| --- | --- |
| 担当者が見る下書きを Django のセッションに置く | 本人以外に見えず、集計もできない |
| クライアントが送ってきた価格や合計額で確定する | 書き換えられた値で注文が確定する |
| 権限をクライアントの値や JWT の中身だけで判断する | 改ざんや、権限を外した後の操作を通す |
| トークンや個人情報を localStorage・URL に置く | XSS・ログ・`Referer` から漏れる |
| ウィザードの状態を `session["wizard"]` 1 つに置く | 2 つのタブで作業すると混ざる |
| プロセスのメモリに状態を置く | ワーカーが複数あると次のリクエストで消える |
| `cache` バックエンドで消えては困る状態を持つ | キャッシュの追い出しで消える |
| 下書きのために集約の不変条件を緩める | 提出済みのデータでも不正な値を許す |
| localStorage や途中状態の JSON に形のバージョンがない | デプロイ後に古い形を読んで壊れる |
| 寿命を決めずに途中状態を保存する | 期限切れのセッションや下書きが溜まり続ける |

## ルール(チェックリスト)

- [ ] 本人以外が見る・規則が依存する・集計する・端末をまたぐものは、業務データとして DB に置いた
- [ ] 検索条件や並び順は URL に置き、共有や戻る操作で再現できる
- [ ] クライアントから届いた価格・ID・権限を、サーバーで検証し直している
- [ ] 往復させるサーバー由来の値は署名し、秘密を入れていない
- [ ] 秘密・トークン・個人情報を localStorage と URL に置いていない
- [ ] プロセスのメモリに状態を置いていない
- [ ] Django のセッションに置く値は JSON にでき、タブをまたいで混ざらない
- [ ] 消えると困る状態を `cache` バックエンドに置いていない
- [ ] 自社の同じサイトの SPA は Cookie のセッションで認証し、CSRF トークンを送っている
- [ ] 下書きは別の型(または途中状態の表)にし、集約の不変条件を緩めていない
- [ ] すべての置き場所に寿命と片付けがあり、保存する形にバージョンがある
